## 摘要

这个 EIP 定义了一个标准接口，用于通过 bytecode 哈希在以太坊上索引智能合约。这实现了对合约代码的无需信任的发现和验证，从而促进 bytecode 签名、白名单和去中心化分发机制等用例。

## 动机

现有的合约发现依赖于地址，这些地址是非确定性的，并且可以通过代理进行混淆。 通过 bytecode 哈希进行索引提供了一种确定性和防篡改的方式来识别和验证合约代码，从而增强了以太坊生态系统中的安全性和信任。

考虑一个想要证明合约代码完整性的安全审计员。 通过引用 bytecode 哈希，审计员可以将其审计重点放在 bytecode 本身上，而无需评估部署参数或存储内容。 这种方法验证了合约代码库的完整性，而无需审计整个合约状态。

此外，bytecode 引用允许在部署之前列入白名单合约，允许开发人员在不披露代码本身的情况下获得其代码库的预先批准，甚至可以预先设置基础设施，这些基础设施会在链上添加某些确定的功能后改变其行为。

对于依赖大量代码重用的开发人员来说，bytecode 引用可以防止通过代理进行基于地址的引用可能发生的恶意更改。 这建立了延伸到最终用户应用程序的长期信任链。

对于去中心化应用程序 (dApp) 开发人员，代码索引可以通过允许他们引用现有代码库而不是重新部署它们来节省 gas 成本，从而优化资源使用。 对于依赖于大量重用与自身依赖项相同的代码库的 dApp 来说，这可能很有用。

### 为什么此注册表需要是 ERC

代码索引对于无需信任且安全的智能合约开发至关重要。 通过标准化通过 bytecode 索引合约的接口，开发人员可以轻松地将此功能集成到他们的智能合约中，从而增强以太坊生态系统的安全性和可信度。

它的简单性和通用性使其适用于广泛的应用。 全局引用相同代码库的能力使其成为标准化的理想选择。

最终，此功能应纳入 EIP 标准，因为它是无需信任且安全的智能合约开发的基本构建块。 此标准是朝着这个目标迈出的一步。

## 规范

本文档中的关键词“必须”，“禁止”，“必需”，“应”，“不应”，“推荐”，“不推荐”，“可以”和“可选”应按照 RFC 2119 和 RFC 8174 中的描述进行解释。

```solidity
// SPDX-License-Identifier: CC0-1.0
pragma solidity 0.8.28;
import {IERC7744} from "./IERC7744.sol";

/**
 * @title Byte Code Indexer Contract
 * @notice 您可以使用此合约通过 bytecode 建立合约索引。
 * @dev 这允许通过 bytecode 而不是地址来查询合约。
 * @author Tim Pechersky (@Peersky)
 */
contract ERC7744 is IERC7744 {
    mapping(bytes32 => address) private index;

    function isEIP7702(address account) public view returns (bool) {
        bytes3 prefix;
        assembly {
            extcodecopy(account, 0, mload(0x40), 3) // 将前 3 个字节复制到内存
            prefix := mload(0x40) // 从内存中加载 3 个字节
        }
        return prefix == bytes3(0xef0100);
    }

    function isValidContainer(address container) private view returns (bool) {
        bytes memory code = container.code;
        bytes32 codeHash = address(container).codehash;
        return (code.length > 0 && codeHash != bytes32(0) && !isEIP7702(container));
    }

    /**
     * @notice 通过 bytecode 哈希在索引中注册合约
     * @param container 要注册的合约
     * @dev 将使用 `msg.codeHash`
     * @dev 如果合约已被索引或返回 EIP7702 委托的 EOA，它将会恢复
     */
    function register(address container) external {
        address etalon = index[container.codehash];
        require(isValidContainer(container), "Invalid container");
        if (etalon != address(0)) {
            if (isValidContainer(etalon)) revert alreadyExists(container.codehash, container);
        }
        index[container.codehash] = container;
        emit Indexed(container, container.codehash);
    }

    /**
     * @notice 通过 bytecode 哈希返回合约地址
     * @dev 如果合约未被索引，则返回零
     * @param id bytecode 哈希
     * @return 合约地址
     */
    function get(bytes32 id) external view returns (address) {
        return index[id];
    }
}
```

### 部署方法

`CodeIndex` 合约部署在：`0xC0De1D1126b6D698a0073A4e66520111cEe22F62`，通过 `CREATE2`，经由确定性部署器 `0x4e59b44847b379578588920ca78fbf26c0b4956c`，使用 salt 值 `0x9425035d50edcd7504fe5eeb5df841cc74fe6cccd82dca6ee75bcdf774bd88d9` 获取，方法是寻找一个有意义的名称“Code ID (`c0de1d`)”开头的 vanity 地址，用于使用 `solc 0.8.28` 编译的 bytecode，如 `solc --input-file src/ERC7744.sol --bin --optimize --optimize-runs 2000 --metadata-hash none --via-ir --optimize-yul`。

## 理由

**Bytecode 优于地址**：Bytecode 是确定性的，可以在链上验证，而地址是不透明且可变的。

**在重新索引时回滚**：存在很小的但非零的哈希冲突攻击的可能性。 不允许更新 bytecode 的索引位置可以避免这种情况。

**简单接口**：该接口非常简洁，专注于最大化可组合性和易于实现。

**库实现**：将此实现为库会限制其影响，使代码重用更加困难，并且缺乏单一的、官方的真实来源。 通过将其确立为 ERC，我们可以确保标准化和广泛采用，从而推动生态系统的发展。

## 安全注意事项

**恶意代码**：索引并不保证索引合约的安全或功能。 用户必须谨慎行事，并在与索引合约交互之前进行自己的尽职调查。

**已注册合约的存储内容**：索引仅指合约的 bytecode，而不是存储内容。 这意味着合约状态未被索引，并且可能会随着时间而变化。

**[EIP-7702]**：索引不索引 EIP-7702 委托的帐户。 在尝试注册期间，它会检查合约代码是否以保留的委托指示符 `0xef0100` 开头，如果是，它将恢复。

**自毁合约**：如果索引合约的存储空间变为空，则可以重新索引合约。在 register 函数调用期间，如果合约已经被索引，我们会在索引地址上运行 `isValidContainer` 检查。 如果检查失败，则允许使用新指定的地址重新索引。
