## 摘要

一个 Javascript Ethereum Provider 接口注入，它将允许多个浏览器钱包同时进行互操作。用 `window.evmproviders` 替换 `window.ethereum` 是一个简单的解决方案，它将提供多重好处，包括：改善用户体验、鼓励该领域的创新、消除竞争条件和“赢者通吃”的环境，以及降低用户采用的门槛。

## 动机

目前，`window.ethereum` 是以太坊兼容应用程序与注入钱包交互的主要方法。这起源于 2015 年的 Mist Wallet，用于与其他应用程序交互。随着应用程序和钱包的普及，`window.ethereum` 产生了意想不到的负面后果：

- `window.ethereum` 每次只允许注入一个钱包，导致两个或多个钱包之间出现竞争条件。这会产生不一致的连接行为，使得拥有和使用多个浏览器钱包变得不可预测和不切实际。目前的解决方案是让钱包注入它们自己的命名空间，但这并不可行，因为每个应用程序都需要知道可能使用的任何钱包。
- 前述的竞争条件意味着用户不愿尝试新的钱包。这在 EVM 链上创建了一个“赢者通吃”的钱包市场，迫使应用程序开发人员针对特定的钱包体验进行优化。
- 由 `window.ethereum` 标准产生的“赢者通吃”钱包环境阻碍了创新，因为它创建了采用的障碍。新进入该领域的参与者很难与传统参与者竞争，因为用户最多只能拥有一个注入的钱包。随着新进入者的退出，传统钱包提供商面临的创新压力很小。
- 钱包仍然是与区块链交互的最基本工具。以太坊和 EVM 链中同质化的钱包体验可能会阻碍整个生态系统的 UX 改进，并允许其他更鼓励竞争和创新的生态系统向前发展。
- 截至 2022 年 8 月，一些当前使用 `window.ethereum` 的钱包。目前，如果用户在单个浏览器中使用多个这些钱包，则会出现不一致的行为。
	- Metamask
	- Coinbase wallet
	- Enkrypt
	- Trust wallet
	- Rainbow
  

用 `window.evmproviders` 替换 `window.ethereum` 将允许 web3modal 和 web3onboard 等解决方案显示用户安装的所有注入钱包。这将简化 UX，并消除多个钱包安装时钱包提供商之间的竞争条件。随着时间的推移，随着 `window.evmproviders` 取代当前标准并消除选择障碍，我们可以希望看到一个更能反映用户偏好的钱包格局。

## 规范

本文档中的关键词“MUST”，“MUST NOT”，“REQUIRED”，“SHALL”，“SHALL NOT”，“SHOULD”，“SHOULD NOT”，“RECOMMENDED”，“MAY”和“OPTIONAL”应按照 RFC 2119 中所述进行解释。

### `window.evmproviders={}`

```typescript
/**
 * 表示显示钱包所需的资产
 */
interface ProviderInfo {
   /**
    * 钱包提供商独有的 UUIDv4。
    *
    * 在不同版本之间必须保持不变，但在不同渠道之间必须不同。例如，MetaMask、Trust wallet 和 Enkrypt 应该各自具有不同的 UUID，但 MetaMask 10.22.2 和 MetaMask 9.8.1 应该具有相同的 UUID。
    *
    * @readonly
    */
    uuid: string;
    /**
     * 钱包提供商的名称（例如 `MetaMask` 或 `Enkrypt`）
     *
     * @readonly
     */
    name: string;
    /**
     * Base64 编码的 SVG 图像。
     *
     * Base64 在 RFC 4648 中定义。
     *
     * @readonly
     */
    icon: `data:image/svg+xml;base64,${string}`;
    /**
     * 钱包提供商的描述。
     *
     * @readonly
     */
    description: string;
}
```

```typescript
/**
 * 表示具有信息类型的新 Provider，它扩展了 EIP1193 provider
 */
interface ProviderWithInfo extends EIP1193Provider {
  	info: ProviderInfo;
}
```

类型 `EIP1193Provider` 记录在 [EIP-1193](./eip-1193.md)

```typescript
/**
 * `window.evmproviders` 的类型
 */
interface EVMProviders {
  /**
   * 建议将 Key 作为扩展名的 snake_case 名称。它必须仅包含小写字母、数字和下划线。
   */
  [index: string]: ProviderWithInfo;
}
```

## 理由

标准化 `ProviderInfo` 类型允许确定填充钱包选择弹出窗口的必要信息。这对于 Web3Modal、Web3React 和 Web3Onboard 等 web3 onboarding 库特别有用。

选择名称 `evmproviders` 是为了包含其他 EVM 兼容链。

选择 SVG 图像格式是因为它的灵活性、轻量级特性和动态调整大小功能。

## 向后兼容性

此 EIP 不需要取代 `window.ethereum`，因此它不会直接破坏现有应用程序。但是，最终取代 `window.ethereum` 的推荐行为将破坏依赖它的现有应用程序。

## 参考实现

### 注入

```typescript
const provider: ProviderWithInfo = [your wallet]
window.evmproviders = window.evmproviders || {};
window.evmproviders[name] = provider
```

### 检索所有 EVM providers

```typescript
const allproviders = Object.values(window.evmproviders)
```

## 安全注意事项

EIP-1193 的安全注意事项适用于此 EIP。

使用 SVG 图像会引入跨站点脚本风险，因为它们可以包含 JavaScript 代码。应用程序和库必须使用 `<img>` 标记呈现 SVG 图像，以确保不会发生 JS 执行。
