## Abstract

There are multiple token standards on Ethereum chain currently. This EIP introduces a concept of cross-standard interoperability by creating a service that allows [ERC-20](./eip-20.md) tokens to be upgraded to [ERC-223](./eip-223.md) tokens anytime.（目前以太坊链上有多种代币标准。 本 EIP 引入了一种跨标准互操作性的概念，通过创建一个服务，允许 [ERC-20](./eip-20.md) 代币随时升级到 [ERC-223](./eip-223.md) 代币。）[ERC-223](./eip-223.md) tokens can be converted back to [ERC-20](./eip-20.md) version without any restrictions to avoid any problems with backwards compatibility and allow different standards to co-exist and become interoperable and interchangeable.（[ERC-223](./eip-223.md) 代币可以不受任何限制地转换回 [ERC-20](./eip-20.md) 版本，以避免任何向后兼容性问题，并允许不同的标准共存并变得可互操作和可互换。）

In order to perform the conversion, a user must deposit tokens of one standard to the Converter contract and it will automatically send tokens of another standard back.（为了执行转换，用户必须将一种标准的代币存入转换器合约，它会自动将另一种标准的代币发送回去。）

## Motivation

This proposal introduces a concept of a token standard upgrading procedure driven by a specialized smart-contract which can convert tokens of one standard to another at any time.（本提案引入了一种代币标准升级过程的概念，该过程由一个专门的智能合约驱动，该合约可以随时将一种标准的代币转换为另一种标准的代币。）

Currently some tokens are available on different chains in different standards, for example most exchanges support [ERC-20](./eip-20.md) USDT, TRX USDT, BEP-20 USDT and all this tokens are in fact the same USDT token.（目前某些代币以不同的标准在不同的链上可用，例如，大多数交易所支持 [ERC-20](./eip-20.md) USDT、TRX USDT、BEP-20 USDT，而所有这些代币实际上都是相同的 USDT 代币。）This proposal is intended to introduce a concept where there can be a [ERC-20](./eip-20.md) USDT and [ERC-223](./eip-223.md) USDT available on Ethereum mainnet at the same time and these would be freely interchangeable.（本提案旨在引入一个概念，即在以太坊主网上可以同时提供 [ERC-20](./eip-20.md) USDT 和 [ERC-223](./eip-223.md) USDT，并且这些代币可以自由互换。）

The address of the deployed Token Converter must be described here as to solve the trust issues for the token developers and help them figure out a proper way of interacting with the Converter.（已部署的代币转换器的地址必须在此处描述，以解决代币开发人员的信任问题，并帮助他们找到与转换器交互的正确方法。）

As Ethereum already has an established ecosystem of tokens and [ERC-20](./eip-20.md) is the most adopted standard at the moment the lack of defined migration processes can be a bottleneck for newer standards adoption.（由于以太坊已经建立了一个完善的代币生态系统，并且 [ERC-20](./eip-20.md) 是目前采用最多的标准，因此缺乏明确的迁移流程可能会成为采用新标准的瓶颈。）This proposal addresses the problem of coordinating the upgrading process and addresses the backwards compatibility problems for [ERC-20](./eip-20.md) and [ERC-223](./eip-223.md) tokens.（本提案解决了协调升级过程的问题，并解决了 [ERC-20](./eip-20.md) 和 [ERC-223](./eip-223.md) 代币的向后兼容性问题。）

The Token Converter is supposed to allow anyone to create an alternative version of an existing token implemented in a different standard.（代币转换器应该允许任何人创建一个以不同标准实施的现有代币的替代版本。）This proposal focuses on [ERC-20](./eip-20.md) and [ERC-223](./eip-223.md) standards and takes into account the specifics of this particular token standards.（本提案侧重于 [ERC-20](./eip-20.md) 和 [ERC-223](./eip-223.md) 标准，并考虑了这种特定代币标准的具体情况。）It is assumed that the most common case would be creation of [ERC-223](./eip-223.md) version for an existing [ERC-20](./eip-20.md) token.（假设最常见的情况是为现有的 [ERC-20](./eip-20.md) 代币创建 [ERC-223](./eip-223.md) 版本。）

The implementation of this service is an alternative to convincing each token developer to choose an alternative standard at the moment of the token deployment or during the development stage of their project.（此服务的实施方案是，无需说服每位代币开发人员在代币部署时或在其项目的开发阶段选择替代标准。）With this service there will be no need to choose one standard and stick with it as every token can be available in both concurrently.（有了这项服务，就不需要选择一种标准并坚持使用它，因为每个代币都可以同时以两种标准提供。）

The implementation of this Token Converter service is supposed to be a contract deployed on Ethereum mainnet once and forever.（此代币转换器服务的实施方案应该是一个在以太坊主网上一次性永久部署的合约。）It's address will be provided in the text of this proposal as to avoid any potential trust issues and assure the developers that the service they are interacting with is exactly the one which drives the conversion process of existing tokens.（本提案的文本中将提供它的地址，以避免任何潜在的信任问题，并确保开发人员与之交互的服务正是驱动现有代币转换过程的服务。）

All the [ERC-223](./eip-223.md) tokens created by the Token Converter will be identical in a way that they all implement the same functions, which return the same values and there is no ambiguity there.（代币转换器创建的所有 [ERC-223](./eip-223.md) 代币都将是相同的，因为它们都实现相同的函数，这些函数返回相同的值，并且没有任何歧义。）This helps to avoid problems where a token deployed during the early stage of a token standard adoption may implement it improperly or there can be an ambiguity in the standard itself that would allow developers to implement tokens of one standard in different ways.（这有助于避免以下问题：在代币标准采用的早期阶段部署的代币可能无法正确实施，或者标准本身可能存在歧义，从而允许开发人员以不同的方式实施一种标准的代币。）

For example it was a common case with [ERC-20](./eip-20.md) where developers could implement custom logic of the `transfer` function and mess the return values.（例如，[ERC-20](./eip-20.md) 的常见情况是，开发人员可以实施 `transfer` 函数的自定义逻辑并搞乱返回值。）The [ERC-20](./eip-20.md) specification declares that a `transfer` function MUST return a `bool` value, however in practice we have three different types of [ERC-20](./eip-20.md) tokens which are not compatible with each other:（[ERC-20](./eip-20.md) 规范声明 `transfer` 函数必须返回一个 `bool` 值，但实际上我们有三种不同类型的 [ERC-20](./eip-20.md) 代币，它们彼此不兼容：）

1. [ERC-20](./eip-20.md) tokens that return `true` on success and revert on an error.（[ERC-20](./eip-20.md) 代币，成功时返回 `true`，出错时恢复。）
2. [ERC-20](./eip-20.md) tokens that return `true` on success and `false` on an error without reverting the transaction.（[ERC-20](./eip-20.md) 代币，成功时返回 `true`，出错时返回 `false`，而不恢复交易。）
3. [ERC-20](./eip-20.md) tokens that don't have return values and revert on an error.（[ERC-20](./eip-20.md) 代币，没有返回值，出错时恢复。）

Technically the third category of tokens is not compatible with [ERC-20](./eip-20.md) standard.（从技术上讲，第三类代币与 [ERC-20](./eip-20.md) 标准不兼容。）However, USDT token deployed on Ethereum mainnet at `0xdac17f958d2ee523a2206206994597c13d831ec7` address does not implement return values and it is one of the most used tokens and it is not an option to deny supporting USDT due to it's improper implementation of the standard.（但是，在以太坊主网上部署在 `0xdac17f958d2ee523a2206206994597c13d831ec7` 地址的 USDT 代币未实现返回值，它是最常用的代币之一，并且由于其对标准的不正确实现，拒绝支持 USDT 是不可接受的。）

The Token Converter eliminates the issue where different development teams may implement the standard with slight modifications and result in a situation where we would have different versions of the same standard on the mainnet.（代币转换器消除了不同开发团队可能对标准进行细微修改并导致我们在主网上拥有同一标准的不同版本的情况。）

At the same time the Converter enables the concurrent token support in other smart-contracts, such as decentralized exchanges.（同时，转换器还可以在其他智能合约（如去中心化交易所）中实现并发代币支持。）The Converter can guarantee that a pair of two tokens one of which is a wrapper for another is in fact the same token that can be converted from one standard to another at any time.（转换器可以保证，一对代币（其中一个代币是另一个代币的包装器）实际上是相同的代币，可以随时从一种标准转换为另一种标准。）This enables the creation of liquidity pools where two different tokens are dealt with as if they were one token.（这使得可以创建流动性池，其中两种不同的代币被视为一种代币进行处理。）

## Specification

The key words "MUST", "MUST NOT", "REQUIRED", "SHALL", "SHALL NOT", "SHOULD", "SHOULD NOT", "RECOMMENDED", "NOT RECOMMENDED", "MAY", and "OPTIONAL" in this document are to be interpreted as described in RFC 2119 and RFC 8174.（本文档中的关键词 "MUST"（必须），"MUST NOT"（禁止），"REQUIRED"（需要），"SHALL"（应该），"SHALL NOT"（不应该），"SHOULD"（应该），"SHOULD NOT"（不应该），"RECOMMENDED"（推荐），"NOT RECOMMENDED"（不推荐），"MAY"（可以）和 "OPTIONAL"（可选）应按照 RFC 2119 和 RFC 8174 中的描述进行解释。）

The Token Converter system comprises two main components:（代币转换器系统包括两个主要组件：）

- Converter contract.（转换器合约。）

- Wrapper contracts. Each original token can have exactly one wrapper of each standard.（包装器合约。每个原始代币对于每种标准都可以有且仅有一个包装器。）

Converter contract can deploy new [ERC-223](./eip-223.md) wrapper contracts for any [ERC-20](./eip-20.md) token that does not have a [ERC-223](./eip-223.md) wrapper currently.（对于当前没有 [ERC-223](./eip-223.md) 包装器的任何 [ERC-20](./eip-20.md) 代币，转换器合约都可以部署新的 [ERC-223](./eip-223.md) 包装器合约。）There MUST be exactly one [ERC-223](./eip-223.md) wrapper for each [ERC-20](./eip-20.md) token.（对于每个 [ERC-20](./eip-20.md) 代币，必须有且仅有一个 [ERC-223](./eip-223.md) 包装器。）

Converter contract MUST accept deposits of [ERC-20](./eip-20.md) tokens and send [ERC-223](./eip-223.md) tokens to the depositor at 1:1 ratio.（转换器合约必须接受 [ERC-20](./eip-20.md) 代币的存款，并以 1:1 的比例将 [ERC-223](./eip-223.md) 代币发送给存款人。）Upon depositing 1234 units of `ERC20 token_A` the depositor MUST receive exactly 1234 units of `ERC223 token_A`.（存入 1234 单位的 `ERC20 token_A` 后，存款人必须收到 1234 单位的 `ERC223 token_A`。）This is done by issuing new [ERC-223](./eip-223.md) tokens at the moment of [ERC-20](./eip-20.md) deposit.（这是通过在 [ERC-20](./eip-20.md) 存款时发行新的 [ERC-223](./eip-223.md) 代币来完成的。）The original [ERC-20](./eip-20.md) tokens MUST be frozen in the Converter contract and available for claiming back.（原始 [ERC-20](./eip-20.md) 代币必须在转换器合约中冻结，并可用于赎回。）

Converter contract MUST accept deposits of [ERC-223](./eip-223.md) tokens and send [ERC-20](./eip-20.md) tokens to the depositor at 1:1 ratio.（转换器合约必须接受 [ERC-223](./eip-223.md) 代币的存款，并以 1:1 的比例将 [ERC-20](./eip-20.md) 代币发送给存款人。）This is done by releasing the original [ERC-20](./eip-20.md) tokens at the moment of [ERC-223](./eip-223.md) deposit.（这是通过在 [ERC-223](./eip-223.md) 存款时释放原始 [ERC-20](./eip-20.md) 代币来完成的。）The deposited [ERC-223](./eip-223.md) tokens must be burned.（存入的 [ERC-223](./eip-223.md) 代币必须被销毁。）

```solidity
function getERC20WrapperFor(address _token) public view returns (address)
```

##### `predictWrapperAddress`

```solidity
function predictWrapperAddress(address _token,
                                   bool    _isERC20 // Is the provided _token a ERC-20 or not?（提供的 _token 是 ERC-20 吗？）
                                                    // If it is set as ERC-20 then we will predict the address of a 
                                                    // ERC-223 wrapper for that token.（如果设置为 ERC-20，那么我们将预测该代币的 ERC-223 包装器的地址。）
                                                    // Otherwise we will predict ERC-20 wrapper address.（否则，我们将预测 ERC-20 包装器的地址。）
                                  ) view external returns (address)
```

Wrapper contracts are deployed via `CREATE2` opcode and it is possible to predict the address of a wrapper which is not yet deployed.（包装器合约通过 `CREATE2` 操作码部署，因此可以预测尚未部署的包装器的地址。）The address of a wrapper contract depends on the bytecode therefore it is necessary to specify if the address of wrapper [ERC-20](./eip-20.md) or wrapper [ERC-223](./eip-223.md) must be predicted.（包装器合约的地址取决于字节码，因此有必要指定必须预测包装器 [ERC-20](./eip-20.md) 或包装器 [ERC-223](./eip-223.md) 的地址。）

Providing `_token` address and `_isERC20 = false` will result in [ERC-20](./eip-20.md) wrapper address being predicted.（提供 `_token` 地址和 `_isERC20 = false` 将导致预测 [ERC-20](./eip-20.md) 包装器地址。）

Providing `_token` address and `_isERC20 = true` will result in [ERC-223](./eip-223.md) wrapper address being predicted.（提供 `_token` 地址和 `_isERC20 = true` 将导致预测 [ERC-223](./eip-223.md) 包装器地址。）

##### `createERC223Wrapper`

```solidity
function createERC223Wrapper(address _erc20Token) public returns (address)
```

Creates a new [ERC-223](./eip-223.md) wrapper for a given `_erc20Token` if it does not exist yet.（如果给定的 `_erc20Token` 尚不存在，则为其创建一个新的 [ERC-223](./eip-223.md) 包装器。）Reverts the transaction if the wrapper already exist.（如果包装器已存在，则恢复交易。）Returns the address of the new wrapper token contract on success.（成功后返回新包装器代币合约的地址。） Reverts if `_erc223Token` is a wrapper created by the Converter.（如果 `_erc223Token` 是转换器创建的包装器，则恢复。）

The deployed contract will be a standard [ERC-223](./eip-223.md) token with `approve` and `transferFrom` functions implemented for backwards compatibility.（部署的合约将是一个标准的 [ERC-223](./eip-223.md) 代币，并为向后兼容性实现 `approve` 和 `transferFrom` 函数。）

All [ERC-223](./eip-223.md) wrappers deployed by the Converter will have `standard() pure returns (bytes32)` function implemented which returns `223`.（转换器部署的所有 [ERC-223](./eip-223.md) 包装器都将实现 `standard() pure returns (bytes32)` 函数，该函数返回 `223`。）This serves further token standard introspection as [ERC-165](./eip-165.md) may not be reliable when dealing with identifying the internal logic implemented within `transfer` function of a token.（这有助于进一步进行代币标准自省，因为在处理识别代币的 `transfer` 函数中实现的内部逻辑时，[ERC-165](./eip-165.md) 可能不可靠。）

NOTE: This function does not verify the standard of `_erc20Token` because there is no reliable method of introspection available which could guarantee that the provided token implements a particular standard.（注意：此函数不验证 `_erc20Token` 的标准，因为没有可靠的自省方法可以保证提供的代币实现特定的标准。）As the result it is possible to create a [ERC-223](./eip-223.md) wrapper for an original [ERC-223](./eip-223.md) token.（因此，可以为原始 [ERC-223](./eip-223.md) 代币创建一个 [ERC-223](./eip-223.md) 包装器。）

##### `createERC20Wrapper`

```solidity
function createERC20Wrapper(address _erc223Token) public returns (address)
```

Creates a new [ERC-20](./eip-20.md) wrapper for a given `_erc223Token` if it does not exist yet.（如果给定的 `_erc223Token` 尚不存在，则为其创建一个新的 [ERC-20](./eip-20.md) 包装器。）Reverts the transaction if the wrapper already exist.（如果包装器已存在，则恢复交易。）Returns the address of the new wrapper token contract on success.（成功后返回新包装器代币合约的地址。） Reverts if `_erc223Token` is a wrapper created by the Converter.（如果 `_erc223Token` 是转换器创建的包装器，则恢复。）

NOTE: This function does not verify the standard of `_erc223Token` because there is no reliable method of introspection available which could guarantee that the provided token implements a particular standard.（注意：此函数不验证 `_erc223Token` 的标准，因为没有可靠的自省方法可以保证提供的代币实现特定的标准。）As the result it is possible to create a [ERC-20](./eip-20.md) wrapper for an original [ERC-20](./eip-20.md) token.（因此，可以为原始 [ERC-20](./eip-20.md) 代币创建一个 [ERC-20](./eip-20.md) 包装器。）

##### `wrapERC20toERC223`

```solidity
function wrapERC20toERC223(address _ERC20token, uint256 _amount) public returns (bool)
```

Withdraws `_amount` of [ERC-20](./eip-20.md) tokens from the transaction sender with `transferFrom` function.（使用 `transferFrom` 函数从交易发送者处提取 `_amount` 个 [ERC-20](./eip-20.md) 代币。）Delivers the `_amount` of [ERC-223](./eip-223.md) wrapper tokens to the sender of the transaction.（将 `_amount` 个 [ERC-223](./eip-223.md) 包装器代币发送给交易发送者。）Stores the original tokens at the balance of the Token Converter contract for future claims.（将原始代币存储在代币转换器合约的余额中，以备将来声明。）Returns `true` on success.（成功后返回 `true`。）The Token Converter must keep record of the amount of [ERC-20](./eip-20.md) tokens that were deposited with `wrapERC20toERC223` function because it is possible to deposit [ERC-20](./eip-20.md) tokens to any contract by directly sending them with `transfer` function.（代币转换器必须记录使用 `wrapERC20toERC223` 函数存入的 [ERC-20](./eip-20.md) 代币的数量，因为可以通过使用 `transfer` 函数直接发送它们来将 [ERC-20](./eip-20.md) 代币存入任何合约。）

If there is no [ERC-223](./eip-223.md) wrapper for the `_ERC20token` then creates it by calling a `createERC223Wrapper(_erc20toke)` function.（如果 `_ERC20token` 没有 [ERC-223](./eip-223.md) 包装器，则通过调用 `createERC223Wrapper(_erc20toke)` 函数来创建它。）

There is no special function to unwrap [ERC-223](./eip-223.md) wrappers to [ERC-20](./eip-20.md) origin as this logic is implemented in the `tokenReceived` function of the Converter.（没有特殊的函数可以将 [ERC-223](./eip-223.md) 包装器解包到 [ERC-20](./eip-20.md) 原始代币，因为此逻辑在转换器的 `tokenReceived` 函数中实现。）

##### `unwrapERC20toERC223`


## 安全考虑

1. 尽管可以实现将任何 token 标准转换为任何其他标准的服务，但最好将不同的标准转换器彼此分开，因为不同的标准可能包含特定的逻辑，因此需要不同的转换方法。本提案侧重于 [ERC-20](./eip-20.md) 和 [ERC-223](./eip-223.md) 的可升级性。
2. [ERC-20](./eip-20.md) token 可以通过 `transfer` 函数直接存入任何合约。这可能会导致 token 的永久性丢失，因为无法在接收方识别出此交易。因此，wrapper-ERC-20 token 容易出现此问题，因为它们与 [ERC-20](./eip-20.md) 标准兼容。`rescueERC20` 函数的实现是为了解决这个问题。
3. Token Converter 依赖于 [ERC-20](./eip-20.md) `approve` 和 `transferFrom` 方法来存入资产。任何相关问题都必须考虑在内。`approve` 和 `transferFrom` 是两个独立的交易，因此在依赖 `transferFrom` 之前，需要确保 `approval` 成功。
4. UI 服务通常会提示用户对任何可能从用户处提取 token 的合约发布无限制的 `approval`，这是一种常见的做法。这会将用户的资金置于风险之中，因此不建议这样做。
5. 没有可靠的 token 标准内省方法可以保证 token 实现了特定的 token 标准。可以人为地构建一个 token，该 token 会假装它是一个实现 `approve & transferFrom` 的 [ERC-20](./eip-20.md) token，但同时实现通过 `transfer` 函数转移的 [ERC-223](./eip-223.md) 逻辑。可以在 Token Converter 中为此 [ERC-20](./eip-20.md)-[ERC-223](./eip-223.md) 混合实现创建一个 [ERC-223](./eip-223.md) wrapper。这不会对 Token Converter 本身的工作流程构成任何威胁，但必须考虑到，如果 token 在 Token Converter 中有 [ERC-223](./eip-223.md) wrapper，这并不意味着来源与 [ERC-20](./eip-20.md) 标准完全兼容，并且必须使用内省方法来确定来源与任何现有标准的兼容性。
6. 由于缺乏可靠的标准内省方法，Token Converter 在被要求为其创建 wrapper 时，不会验证提供的 token 的标准。可以调用 `createERC20Wrapper` 函数并提供现有 [ERC-20](./eip-20.md) token 的地址。Token Converter 将成功地为该 [ERC-20](./eip-20.md) 原始 token 创建一个 [ERC-20](./eip-20.md) wrapper。也可以为该确切的原始 [ERC-20](./eip-20.md) token 创建一个 [ERC-223](./eip-223.md) wrapper。这不会对 Converter 的工作流程构成任何威胁，但必须考虑到，任何 token 无论其原始标准如何，都可能具有 Converter 创建的最多两个 wrapper，每个标准一个。任何 wrapper token 必须只有一个来源。无法为 wrapper 创建 wrapper。
7. Token Converter 仅持有在转换过程中存入的原始 token，并且它假设 token 不会随着时间的推移而衰减，并且 Converter 的 token 余额不会自行减少。如果某些 token 实现了燃烧逻辑或衰减供应，并且可能会影响 Converter 的余额，则不得使用 Converter 部署该 token 的替代版本，因为它将无法保证随时都有足够的 token 用于转换。
