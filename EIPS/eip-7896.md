## 摘要

此 EIP 通过新的 `interfaces` 功能扩展了 [EIP-5792](./eip-5792.md)，应用程序可以使用该功能附加合约接口规范（又名 ABI），钱包需要这些规范来可靠地解码请求中的 calldata。

## 动机

以太坊账户的安全模型依赖于应用程序和钱包之间的关注点分离，后者负责保护私钥材料并提供对其的受限访问。当应用程序请求交易或签名时，钱包会提示用户接受或拒绝它。用户应该对操作的期望效果进行评估，因为它可能会对所有账户资产进行操作，在极端情况下，会为了攻击者的利益“耗尽”所有资产。钱包的任务是提供有关请求的信息，以进行准确的评估，特别是帮助检测意外影响和攻击。

这种理想化的愿景还远未实现。“盲签名”，即在没有完全了解其内容或理解其含义的情况下接受请求的做法，是以太坊中普遍存在的问题。鉴于利害关系，这是一个令人费解的情况。一个可能的解释是，钱包要提取和提供有关请求的良好信息非常困难。

在接受交易请求之前，用户最好确切地知道该交易在链上包含时会产生什么影响。近年来，交易模拟已在钱包中广泛普及，钱包（或服务提供商）运行该交易并将观察到的效果总结为友好的描述，例如“ -1 ETH，+2400 USDC”。但是，由于可变共享状态，完全预测这些影响是不可能的，并且由于 EVM 的图灵完备性，描述可能影响的范围是棘手的，因此我们应该谨慎行事，不要过度依赖这种方法。

交易模拟试图深入了解交易的动态行为，而钱包还应显示所有静态可用信息，例如交易参数和应用程序元数据。

某些参数具有明确的语义，例如，交易中的 `value` 表示转移了多少原生代币。但是，事务中的 `data` 提出了一个挑战，因为它作为字节字符串提供给钱包，并且在不知道目标合约 ABI 的情况下，无法将其可靠地解码为更有意义的结构化信息。钱包可以尝试使用函数选择器数据库来尝试猜测 ABI，但这对于新的和未知的合约将失败，并且已知的选择器可能会由于冲突而产生歧义，包括攻击者故意引入的冲突。或者，钱包可以从经过验证的源代码存储库中获取 ABI，缺点是该主要存储库由中心化方管理。

由于请求交易的应用程序必然知道相关的 ABI，因此本 EIP 提出了一种机制，应用程序可以在交易请求中附加 ABI，以便钱包可以向用户显示解码后的调用数据，并帮助做出更明智的评估。

## 规范

本文档中的关键词“必须”，“不得”，“必需”，“应”，“不应”，“建议”，“不建议”，“可以”和“可选”应按照 RFC 2119 和 RFC 8174 中描述的方式进行解释。

一个新的名为 `interfaces` 的功能被添加到 EIP-5792 请求中。

### `wallet_sendCalls`

当支持此功能时，`wallet_sendCalls` 请求可能包含一个全局 `interfaces` 字段。

应用程序提供的 `interfaces` 字段必须将合约地址映射到接口规范。这些合约地址应与请求的 `calls` 数组中 `to` 字段的地址相对应，并且应以区分大小写的方式进行比较。`calls` 中可能存在没有匹配接口规范的地址，并且 `interfaces` 中可能存在没有匹配调用的地址。

```typescript
type SendCallsParams = { // default fields omitted
    capabilities?: { interfaces?: InterfacesCapability } & Record<string, Capability>;
};

type InterfacesCapability = {
    [contract: `0x${string}`]: {
        version: string;
        spec: unknown; // version-dependent
    };
    optional?: boolean;
};
```

接口规范必须描述合约如何将 calldata 解码为一系列函数参数。将规范解释为解码过程取决于版本字符串。

最初定义的两个版本是 `abi-v1` 和 `abi-v2`，它们对应于 Solidity 定义的合约应用程序二进制接口，并被其他语言采用。在这些情况下，必须按照 Solidity 文档“合约 ABI 规范”的“JSON”部分中的描述，将规范作为数组提供。该数组除了函数描述外，还可以包含事件和错误描述，尽管应用程序应排除不相关的项目。v1-v2 区别对应于 Solidity 的 `pragma abicoder v1` 和 `pragma abicoder v2`（或 `pragma experimental ABIEncoderV2`）。Vyper 实现了 `abi-v2`。

应用程序应将 `interfaces` 字段标记为 `optional`，以便用户在其钱包不支持该功能或提供的规范版本时能够继续进行操作。如果该字段标记为 `optional`，则钱包可以忽略具有不受支持的规范版本的接口。

钱包应使用提供的接口规范来解码 `calls` 数组中每个调用的 `data`，以便向用户呈现解码后的函数参数。钱包可以根据经过验证或受信任的规范数据库来验证提供的规范。

#### 示例请求

```JSON
[
  {
    "version": "1.0",
    "from": "0xa22cc169386b820ab57c006a5b4980add068a7eb",
    "chainId": "0x01",
    "calls": [
      {
        "to": "0xdac17f958d2ee523a2206206994597c13d831ec7",
        "value": "0x00",
        "data": "0xa9059cbb000000000000000000000000f0c87f351435211efa00938a33771bf38302d1f10000000000000000000000000000000000000000000000056bc75e2d63100000"
      }
    ],
    "capabilities": {
      "interfaces": {
        "optional": true,
        "0xdac17f958d2ee523a2206206994597c13d831ec7": {
          "version": "abi-v1",
          "spec": [
            {
              "type": "function"
              "name": "transfer",
              "stateMutability": "nonpayable",
              "inputs": [
                {
                  "name": "to",
                  "type": "address"
                },
                {
                  "name": "value",
                  "type": "uint256"
                }
              ],
              "outputs": [],
            }
          ]
        }
      }
    }
  }
]
```

### `wallet_getCapabilities`

在 `interfaces` 功能下，钱包必须包含一个 `versions` 数组字段，列出支持的接口规范版本。

#### 示例响应

```JSON
{
  "0x0": {
    "interfaces": {
      "supported": true,
      "versions": ["abi-v1", "abi-v2"]
    }
  }
}
```
