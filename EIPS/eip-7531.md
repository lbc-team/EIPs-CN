## 摘要

当 [ERC-721](./eip-721.md) 代币被质押到池中时，其所有权会带来挑战，尤其是在涉及较旧的、不可锁定的 NFT 时，例如 Crypto Punks 或 Bored Ape Yacht Club (BAYC) 代币。本提案引入了一个接口来解决这些挑战，允许质押的 NFT 被其原始所有者识别，即使在它们被质押之后。

## 动机

最近的解决方案包括在“锁定” NFT 时保留 NFT 所有权，从而让所有者保留其所有权。但是，这需要 NFT 合约实现可锁定功能。早期的 NFT 最初并未设计为可锁定的，因此必须质押，并将所有权转移到质押合约。

这会阻止原始所有者访问与其 NFT 相关的有价值的特权和收益。

例如：

- BAYC NFT 持有者在质押后将失去对 BAYC Yacht Club 和会员活动的访问权限。
- CryptoPunks 持有者可能会错过仅对经过验证的所有者提供的特殊空投或展示。
- 其他早期 NFT（如 EtherRocks）的所有者在质押后将失去可证明所有权的社会地位。

通过维护原始所有者的记录，所提出的接口允许这些原始特权保持可访问，即使 NFT 质押在其他地方。对于缺乏原生锁定机制的旧 NFT 项目，这种兼容性至关重要。

另一个重要的权利是使用资产的权利。例如，NFT 可用于玩游戏。如果 NFT 被借给用户，则 NFT 的所有权将转移到借贷合约。在这种情况下，很难识别有权在游戏中使用 NFT 的钱包，而该钱包应该是用户。

该接口提供了一种简单、优雅的方式来将质押兼容性扩展到旧版 NFT，而不会影响其核心功能或所有权收益。

## 规范

本文档中的关键词“必须”、“禁止”、“必需”、“应”、“不应”、“推荐”、“不推荐”、“可以”和“可选”应按照 RFC 2119 和 RFC 8174 中的描述进行解释。

接口定义如下：

```solidity
interface IERC7531 {

  /**
   * @notice 当代币的技术所有者（持有代币的合约）与其实际所有者（拥有代币权利的实体）不同时，必须发出
   * @dev 这种情况在质押中很常见，其中质押合约是技术所有者。 事件必须
   *      在与代币的 Transfer 事件相同的或任何后续区块中发出。
   *      涉及同一代币的后续 Transfer 事件将取代此 RightsHolderChange 事件。
   *      为了确保真实性，监听此事件的实体必须验证
   *      发出事件的合约是否与相关 Transfer 事件的代币的当前所有者匹配。
   *
   * @param tokenAddress 代币合约的地址。
   * @param tokenId 代币的 ID。
   * @param holder 代币的实际权利持有者的地址。
   * @param right 持有者持有的权利类型。 最初支持的权利有：
   *
   *           0x399d2b36   // bytes4(keccak256("ownership"))
   *           0x230a5961   // bytes4(keccak256("usage"))
   *
   *        这允许项目添加更多权利，而不会破坏与此接口的兼容性。 详见 IERC7531Rights。
   */
  event RightsHolderChange(address indexed tokenAddress, uint256 indexed tokenId, address indexed holder, bytes4 right);

  /**
   * @dev 返回拥有代币权利的实体的地址，与当前所有者不同。
   *      如果代币不存在或当前未被持有，则该函数必须恢复。
   *
   * @param tokenAddress ERC-721 合约的地址。
   * @param tokenId 代币的 ID。
   * @param right 持有者持有的权利类型。
   * @return 拥有代币权利的实体的地址。
   */
  function rightsHolderOf(
    address tokenAddress,
    uint256 tokenId,
    bytes4 right
  ) external view returns (address);
}
```

`RightsHolderChange` 事件对于准确识别所持代币的实际所有者至关重要。 在代币质押到合约中的情况下，[ERC-721](./eip-721.md) Transfer 事件会将所有权错误地分配给质押合约本身。 `RightsHolderChange` 事件通过明确指示代币权利的实际所有者来解决此差异。

### 事件发送时机：

`RightsHolderChange` 事件必须在与相应的 `Transfer` 事件相同的区块中或在任何后续区块中发出。 这种方法为现有池提供了升级其系统的灵活性，而不会影响过去的兼容性。 具体来说，质押池可以为所有先前质押的代币发出此事件，或者他们可以允许用户主动收回他们的所有权。 这种灵活性确保系统可以适应当前和未来的状态，同时准确反映所持代币的实际所有权。

### 前一个 `RightsHolderChange` 事件的无效化：

为了保持与更广泛的生态系统的兼容性并优化 gas 效率，任何涉及同一代币的新 `Transfer` 事件都会使任何先前的 `RightsHolderChange` 事件失效。 这种方法确保最新的 `Transfer` 事件可靠地反映当前的所有权状态，而无需在取消质押时发出其他事件。

### NFT 扩展

两个默认权利是：
* 0x399d2b36   // bytes4(keccak256("ownership"))
* 0x230a5961   // bytes4(keccak256("usage"))

但是，可能有一些 NFT 只需要验证所有权，另一些可能需要验证使用情况，还有一些可能需要同时验证两者，还有一些 NFT 可能需要管理完全不同的权利。

为了给 NFT 提供必要的灵活性，我们还提出了以下可选扩展。

```solidity
interface IERC7531Rights {
  
  /**
   * @dev 返回 NFT 支持的权利列表。
   * @return NFT 支持的权利列表。
   */
  function supportedERC7531Rights() external view returns (bytes4[] memory);
  
  /**
   * @dev 返回 NFT 是否支持特定权利。
   * @param right 要检查的权利。
   * @return NFT 是否支持该权利。
   */
  function supportsERC7531Right(bytes4 right) external view returns (bool);
}
```

它允许 NFT 返回它们支持的权利列表，并允许项目验证 NFT 是否支持特定权利。 由于权利由权利名称的 bytes4 哈希值标识，因此在引入新权利时，NFT 项目应公开声明与 bytes4 哈希值对应的字符串，并解释其基本原理。

如果 NFT 不支持该接口（例如，如果是一个现有的 NFT），则使用 NFT 的项目应只考虑标准权利。

NFT 项目应尽可能遵守预先存在的权利，以避免权利的扩散，这可能会使系统效率降低和复杂性增加。

## 原理

### 解决不可锁定 NFT 的挑战：

不可锁定的 NFT 在去中心化生态系统中提出了独特的挑战，尤其是在涉及质押或委托使用权的情况下。 标准 [ERC-721](./eip-721.md) `ownerOf` 函数返回 NFT 的当前所有者，在质押的情况下，这将是质押池合约。 这种将所有权转移到质押池的行为（即使是临时的）可能会扰乱与 NFT 相关的效用或特权，例如参与治理、访问独家内容或在特定生态系统中的效用。

### `rightsHolderOf` 方法：

`rightsHolderOf` 方法为这一挑战提供了一个解决方案。 通过维护与 NFT 相关的某些特权的原始所有者或合法持有者的记录，此方法可确保 NFT 的基础效用得到保留，即使 NFT 本身保存在池中也是如此。

### 技术优势：

1. 效用保留：这种方法允许 NFT 所有者在质押池或其他智能合约中利用他们的资产，而不会失去与 NFT 相关的利益。 这对于赋予持续利益或权利的 NFT 尤其重要。

2. 增强的灵活性：该方法为 NFT 所有者提供了更大的灵活性，允许他们参与质押和其他 DeFi 活动，而不会放弃其 NFT 的内在利益。

3. 兼容性和互操作性：通过引入一种新方法而不是更改现有的 ownerOf 函数，此 EIP 确保与现有的 [ERC-721](./eip-721.md) 合约的向后兼容性。 这对于在 NFT 领域的各种平台和应用程序之间保持互操作性至关重要。

4. 事件驱动的更新：`RightsHolderChange` 事件有助于实时跟踪 NFT 的权利持有人。 这对于依赖最新的所有权信息来提供服务或特权的第三方平台和服务尤其有用。

### 解决潜在的滥用：

虽然这种方法引入了一层复杂性，但同时也有必要进行尽职的实施以防止滥用，例如错误地分配权利。 此 EIP 概述了安全注意事项和最佳实践，以减轻此类风险。

## 向后兼容性

此标准与现有的 [ERC-721](./eip-721.md) 合约完全向后兼容。 只要他们选择采用它，它就可以与现有的可升级质押池无缝集成。 它不需要更改 [ERC-721](./eip-721.md) 标准，而是作为质押池的增强功能。

## 安全考虑

此接口的一个潜在风险是质押池将所有权不正确地分配给不同的钱包。 这可能允许该钱包访问与 NFT 相关的特权，这可能不是真正所有者的意图。 但是，重要的是要注意，这种风险低于将 NFT 的全部法律所有权转移到质押池，因为该接口仅允许识别质押者，而不是替换链上的实际所有者。

### 事件真实性：

对于可能伪造 `RightsHolderChange` 事件的发送存在担忧。 由于任何合约都可以发送此类事件，因此存在错误信息或歪曲所有权的风险。 对于监听 `RightsHolderChange` 事件的实体来说，验证发送事件的合约确实是代币的当前所有者至关重要。 这种验证对于确保所有权信息的准确性并减轻与欺骗性事件发送相关的风险至关重要。

### 降低不准确的所有权记录的风险：

虽然不正确地使用此接口会带来一些不准确的所有权记录的风险，但这是任何质押安排中固有的问题。 由于所有者保留了托管权而不是转移所有权，因此在某种程度上减轻了风险。

### 尽职调查：

特权授予型 NFT 的消费者在评估质押提供商时应进行尽职调查。 应仔细评估管理不善或欺诈的迹象。 该接口本身不会启用新的操作功能，但在与智能合约和质押池交互时，谨慎总是明智的。
