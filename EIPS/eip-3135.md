## 简述

该标准定义了一种代币，该代币只能由代币发行者通过付款人的签名来声明。

## 概要

本 EIP 定义了一组对默认代币标准的补充，例如 ERC-20，它允许在线/离线服务提供商通过签名和验证关于链下代币消耗的消息来与任意数量的用户建立小额支付通道。使用此机制将减少参与者与区块链的交互，从而节省 gas 并提高性能。

## 动机

本 EIP 有两个主要目的，一是减少与区块链的交互，二是将以太坊与现实世界的支付问题联系起来。

许多小型企业希望建立基于区块链的支付系统，但发现这很困难。基本上有两种方法：

1. 直接用代币支付。有很多钱包可以接收和转移代币，但以太坊上的交易需要 gas 并且需要时间来确认。
2. 用户在支付智能合约上锁定代币，服务提供商使用用户签名的支付消息来释放代币，从而建立一个小额支付通道。优点是减少了与区块链的交互，并且签名/验证过程是链下的。但是与支付合约交互需要服务提供商构建 DApp，这需要许多小型企业没有的资源。即使他们设法构建了 DApp，它们也都不同，没有标准化。此外，用户应该有一个带有 DApp 浏览器的钱包，并且必须学习如何使用它。

本 EIP 有助于标准化小额支付系统的交互，并使钱包未来能够构建通用的 UI。

### 签名

生成 ECDSA 签名的伪代码：
```
sign(keccak256(abi_encode(
    "\x19Ethereum Signed Message:\n32", 
        keccak256(abi_encode(
            token_address,
            payer_address,
            token_issuer,
            token_consumption,        // 由用户客户端计算
            epoch
        ))
    ))
,private_key)

```

### 验证过程

验证包括对签名和 token_consumption 的检查

验证服务器运行的伪代码如下：

```

serving_loop:

    for {
        /**
         * unpaied_consumption 由提供商计算
         * signed_consumption 是可声明的金额
         * tolerance 允许付款人在一定程度上“欠”提供商
        */
        // getSignedConsumption 返回已经可以声明的金额
        if(unpaied_consumption <  signed_consumption + tolerance){
            informUser("user need charge", unpaied_consumption)
            interruptService() 
        }else{
            isServing() || recoverService()
        }
    }

verification_loop:

    for {
        message = incomingMessage()
        if(recover_signer(message, signature) != payer_address){
            informUser("check signature failed", hash(message))
            continue
        }

        /**
        * 可选：当使用回显服务器在验证服务器之间同步消息时
        * 有关此内容的更多信息，请参阅安全考虑部分
        */
        if(query(message) != message){
            informUser("message outdate", hash(message))
            continue   
        }

        if(epoch != message.epoch || message.consumption > getDepositBalance()){
            informUser("invalid message", epoch, unpaied_consumption)
            continue
        }
       
        signed_consumption = message.consumption
        save(message)
    }
    
claim_process:

    if(claim()){
        unpaied_consumption -= signed_consumption
        signed_consumption = 0
        epoch+=1
    }

```
### 关于 withdraw

withdraw 函数根据业务模型略有不同

1. 预付款模型

在预付款业务模型中，例如使用代币作为普通商店的充值卡，用户提前向商店支付（加密）货币，以获得可声明的代币作为充值卡（带有奖励或折扣）。结账时，客户将更新后的消费消息（旧消费 + 本次消费）签名给商店，商店在链下验证此消息。购物过程循环进行，不涉及任何区块链，直到客户想要退卡并取回资金。因为商店已经持有所有货币，所以 withdraw 函数应该由代币发行者（商店）执行，以在声明后退还剩余的存款余额。预付款模型可以很容易地构建到具有二维码扫描功能的钱包中。

2. 锁定-释放模型

如果我们运行接受代币作为支付的付费端到端加密电子邮件服务，我们可以使用锁定-释放模型。与预付款不同，我们为发送给 N 个收件人的电子邮件收取 X * N 个代币。在这种“按使用付费”的场景中，服务的计数发生在客户端和服务器端。客户端不应信任服务器给出的收费金额，以防服务器出现故障或恶意行为。当客户端决定不信任服务器时，它会停止签署消息，但一些代币会被扣为人质，保存在存款余额中。为了解决这个问题，withdraw 函数应该由付款人帐户执行，并具有诸如一个月内 epoch 没有变化的限制。

## 原理

本 EIP 针对 ERC-20 代币，因为其已被广泛采用。但是，此扩展旨在与其他代币标准兼容。

我们选择在代币合约中而不是在单独的记录合约中实现这些功能的原因如下：
- 代币可以转移比与 DApp 交互更方便、更通用
- 代币更标准化，并具有更好的 UI 支持
- 代币等于服务，使代币经济更加繁荣
- 移除 approve 流程

## 向后兼容性

本 EIP 完全向后兼容，因为它的实现扩展了 [ERC-20](./eip-20.md) 的功能。

## 实现

```solidity

mapping (address => StampBalance) private _depositBalance;
    
struct StampBalance{
    uint256 balance;
    uint256 epoch;
}
    
function deposit(uint256 value) override external{
    require(value <= _balances[msg.sender]);
    _balances[msg.sender] = _balances[msg.sender].sub(value);
    _depositBalance[msg.sender].balance = _depositBalance[msg.sender].balance.add(value);
    emit Deposit(msg.sender, value);
}

function withdraw(address to, uint256 value) override onlyIssuer external{
    require(value <= _depositBalance[to].balance);
    _depositBalance[to].balance = _depositBalance[to].balance.sub(value);
    _depositBalance[to].epoch += 1;
    _balances[to] = _balances[to].add(value);
    emit Withdraw(to, value);
}
    
function depositBalanceOf(address user) override public view returns(uint256 depositBalance, uint256 epoch){
    return (_depositBalance[user].balance, _depositBalance[user].epoch);
}

// 预付款模型
function claim(address from, uint credit, uint epoch, bytes memory signature) override onlyIssuer external{
    require(credit > 0);
    require(_depositBalance[from].epoch + 1 == epoch);
    require(_depositBalance[from].balance >= credit);
    bytes32 message = keccak256(abi.encode(this, from, _issuer, credit, epoch));
    bytes32 msgHash = prefixed(message);
    require(recoverSigner(msgHash, signature) == from);
    _depositBalance[from].balance = _depositBalance[from].balance.sub(credit);
    _balances[_issuer] = _balances[_issuer].add(credit);
    _depositBalance[from].epoch += 1;
    emit Claim(from, msg.sender, credit, epoch);
}

function prefixed(bytes32 hash) internal pure returns (bytes32) {
    return keccak256(abi.encode("\x19Ethereum Signed Message:\n32", hash));
}

function recoverSigner(bytes32 message, bytes memory sig) internal pure  returns (address) {
    (uint8 v, bytes32 r, bytes32 s) = splitSignature(sig);
    return ecrecover(message, v, r, s);
}

function splitSignature(bytes memory sig) internal pure returns (uint8 v, bytes32 r, bytes32 s) {
    require(sig.length == 65);
    assembly {
        r := mload(add(sig, 32))
        s := mload(add(sig, 64))
        v := byte(0, mload(add(sig, 96)))
    }
    return (v, r, s);
}

```

## 安全考虑

通过将 claim 函数限制为发行者，链层上不存在竞争条件。但是，当发行者使用多个验证器且付款人同时签署多个付款消息时，可能会发生双重支出问题。虽然只有具有最大消费量的消息才能被声明，但其中一些消息可能有机会被检查为有效。可以通过引入回显服务器来解决此问题，该服务器接受来自验证器的消息，按顺序返回具有最大消费量和最大 epoch 编号的消息。如果验证器得到的答案与他发送的消息不同，它会从回显服务器更新消息，作为它收到的最后一条消息以及有关此付款人状态的本地存储。然后，验证器再次要求付款人提供新消息。
