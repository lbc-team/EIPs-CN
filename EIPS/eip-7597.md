# EIP: [ERC-2612](./eip-2612.md) Permit 的合约签名验证扩展

## 摘要

本提案旨在扩展现有 [ERC-2612](./eip-2612.md) Permit 的功能，以支持由智能合约钱包发起的无 Gas [ERC-20](./eip-20.md) 授权操作。

## 动机

当前 [ERC-2612](./eip-2612.md) 中基于 V、R、S 参数的签名验证方案将签名验证限制为 EOA 钱包。

随着智能合约钱包的日益普及和 [ERC-1271](./eip-1271.md) 的采用增加，有必要允许灵活的签名验证方法以及在每个合约的签名验证中使用自定义逻辑。通过接受非结构化的签名字节作为输入，可以使用自定义算法和签名方案，从而支持更广泛的钱包类型。

## 规范

符合规范的合约必须使用以下规范实现 `permit`：

```
function permit(address owner, address spender, uint value, uint deadline, bytes memory signature) external
```
以及先前由 [ERC-2612](./eip-2612.md) 规定的其他两个接口：
```
function nonces(address owner) external view returns (uint)
function DOMAIN_SEPARATOR() external view returns (bytes32)
```

对 `permit(owner, spender, value, deadline, signature)` 的调用会将 `allowance[owner][spender]` 设置为 value，将 `nonces[owner]` 递增 1，并发出相应的 `Approval` 事件，当且仅当满足以下条件时：

- 当前区块时间小于或等于 `deadline`。
- `owner` 不是零地址。
- `nonces[owner]`（在状态更新之前）等于 nonce。
- `signature` 验证：
    - 如果 `owner` 是 EOA，则 `signature` 是 `abi.encodePacked(r, s, v)` 形式的有效 secp256k1 签名。
    - 如果 `owner` 是合约，则通过调用 `owner` 合约上的 `isValidSignature()` 来验证 `signature`。

如果未满足上述任何条件，则 permit 调用必须回退。

## 原理

通过替换现有的 V、R、S 签名验证方案并引入对非结构化字节输入的支持，合约开发者可以使用统一的接口来验证来自 EOA 和 SC 钱包的签名。这允许利用适合钱包类型的不同签名方案和算法，从而为智能合约钱包和高级钱包类型增强其签名验证流程铺平道路，从而提高灵活性和创新性。

## 向后兼容性

本提案与现有的 ERC-2612 标准完全向后兼容。当前依赖于 V、R、S 签名验证方案的合约将继续运行，而不会出现任何问题。

如果出于向后兼容性的原因需要同时支持 V、R、S 签名验证和新的非结构化字节签名验证，则开发者可以通过采用以下代码块作为示例来减少重复：

```
function permit(
    address owner,
    address spender,
    uint256 value,
    uint256 deadline,
    uint8 v, 
    bytes32 r, 
    bytes32 s
) external {
    _permit(owner, spender, value, deadline, abi.encodePacked(r, s, v));
}
```

## 参考实现

使用 OZ 的 SignatureChecker 实现的示例 `permit`

```solidity
/**
 * @notice 使用签名许可更新授权额度
 * @dev 签名字节可用于 EOA 钱包和合约钱包。
 * @param owner       Token 所有者的地址（授权者）
 * @param spender     Spender 的地址
 * @param value       授权额度
 * @param deadline    签名过期的日期（unix 时间）
 * @param signature   EOA 钱包或合约钱包签署的非结构化字节签名
 */
function permit(
    address owner,
    address spender,
    uint256 value,
    uint256 deadline,
    bytes memory signature
) external {
    require(deadline >= now, "Permit is expired");
    require(owner != address(0), "ERC20: approve from the zero address");
    require(spender != address(0), "ERC20: approve to the zero address");

    bytes32 digest = keccak256(abi.encodePacked(
        hex"1901",
        DOMAIN_SEPARATOR,
        keccak256(abi.encode(
            keccak256("Permit(address owner,address spender,uint256 value,uint256 nonce,uint256 deadline)"),
            owner,
            spender,
            value,
            nonce,
            deadline
        ))
    ));
    
    require(
        // 同时检查 ECDSA 签名和 ERC-1271 签名。SignatureChecker 示例可在
        // https://github.com/OpenZeppelin/openzeppelin-contracts/blob/7bd2b2a/contracts/utils/cryptography/SignatureChecker.sol
        SignatureChecker.isValidSignatureNow(
            owner,
            typedDataHash,
            signature
        ),
        "Invalid signature"
    );
    
    allowed[owner][spender] = value;
    emit Approval(owner, spender, value);
}
```

## 安全注意事项

- 对于合约钱包，`permit` 的安全性取决于 `isValidSignature()`，以确保签名字节代表来自合约钱包所有者的所需执行。合约钱包开发者在实现自定义签名验证逻辑时必须谨慎，以确保其合约的安全性。
