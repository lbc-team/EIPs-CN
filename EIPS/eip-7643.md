## 摘要

定义了一个 SSZ 对象，用于累积所有 PoS 前的数据，并提交到历史哈希累加器的根
`0xec8e040fd6c557b41ca8ddd38f7e9d58a9281918dc92bdb72342a38fb085e701`。

## 动机

我们考虑历史哈希累加器主要有两个用途：

* 对于希望下载执行链的 PoS 前数据并在不执行每个块的情况下验证它的用户，他们可以简单地计算每个块的哈希值，累积 epoch 记录，然后将本地累加器根与预期值进行比较。
* 此外，累加器根允许对任何 PoS 前区块进行 `O(log(n))` 大小的证明，而今天要实现类似的目标，必须递归地验证头部链。

## 规范

### 历史哈希累加器

历史哈希累加器提交到合并前的头部集合及其相关的总难度。此数据的格式定义为：

```python
EPOCH_SIZE = 8192 # blocks
MAX_HISTORICAL_EPOCHS = 2048

# An individual record for a historical header.
HeaderRecord = Container[block_hash: bytes32, total_difficulty: uint256]

# The records of the headers from within a single epoch
EpochRecord = List[HeaderRecord, max_length=EPOCH_SIZE]

HistoricalHashesAccumulator = Container[
    historical_epochs: List[bytes32, max_length=MAX_HISTORICAL_EPOCHS],
    current_epoch: EpochRecord,
]
```

### Pre-PoS 根

区块 15537394 之前数据的 `HistoricalHashesAccumulator` 的哈希树根是
`0xec8e040fd6c557b41ca8ddd38f7e9d58a9281918dc92bdb72342a38fb085e701`。

## 基本原理

### 包含总难度

允许总难度，以便客户端可以返回支持它的特定 JSON-RPC 方法的值。它对于验证最终工作量证明区块的 TTD 也很有用。

不适用

## 摘要

以下标准定义了一组智能合约中的最小接口，以允许管理、所有和交易不可替代代币。

## 动机

该标准通过提供所有以太坊链上不可替代代币的通用 API 来实现可重用性。该标准提供了一些功能，包括：

*   跟踪特定 NFT 的所有者。
*   授权第三方代表所有者转移 NFT。
*   NFT 的透明交易。
*   允许单个合约跟踪无限数量的 NFT。
*   一个最小的元数据，用于发现和丰富 NFT。

## 规范

关键词“必须”、“不得”、“需要”、“应”、“不应”、“应该”、“不应该”、“推荐”、“不推荐”、“可以”和“可选”在本文件中应按 [RFC 2119](https://tools.ietf.org/html/rfc2119) 中的描述进行解释。

### 概述

*   每个 NFT 必须由合约中的一个唯一的 `uint256` ID 标识。
*   合约*必须*实现 `IERC721` 接口（见下文）。
*   合约*可以*实现 `IERC721Metadata` 接口（见下文）。
*   合约*可以*实现 `IERC721Enumerable` 接口（见下文）。
*   `owner` 总是指地址。
*   对不存在的 NFT ID 执行的调用*必须*还原。
*   交易的实施者*必须*检查消息调用者是否被授权转移 NFT。有以下几种授权：
    *   NFT 的所有者
    *   经所有者授权的运营商
    *   经所有者授权的已批准地址
*   交易的实施者*必须*遵从以下安全转移函数：
    *   `safeTransferFrom(address,address,uint256,bytes)`
    *   `safeTransferFrom(address,address,uint256)`
    *   当接收合约未实现 `IERC721Receiver` 时，或者接收合约实现了 `IERC721Receiver` 但 `IERC721Receiver.onERC721Received` 返回错误代 signature 时，安全转移函数会还原。
*   合约*必须*在任何所有权转移时发出 `Transfer` 事件。
*   合约*必须*在任何授权更改时发出 `Approval` 事件。
*   合约*必须*在任何运营商授权时发出 `ApprovalForAll` 事件。

### IERC721

```solidity
pragma solidity ^0.8.0;

/**
 * @dev Interface of the ERC721 standard as defined in the EIP.
 */
interface IERC721 {
    /**
     * @dev Emitted when `tokenId` token is transferred from `from` to `to`.
     *
     * Requirements:
     *
     * - `from` cannot be the zero address.
     * - `to` cannot be the zero address.
     * - `tokenId` token must be owned by `from`.
     */
    event Transfer(address indexed from, address indexed to, uint256 indexed tokenId);

    /**
     * @dev Emitted when `owner` enables `approved` to manage the `tokenId` token.
     *
     * Requirements:
     *
     * - `tokenId` must exist.
     */
    event Approval(address indexed owner, address indexed approved, uint256 indexed tokenId);

    /**
     * @dev Emitted when `owner` enables or disables (`approved`) `operator` to manage all of its assets.
     */
    event ApprovalForAll(address indexed owner, address indexed operator, bool approved);

    /**
     * @dev Returns the number of tokens in ``owner``'s account.
     */
    function balanceOf(address owner) external view returns (uint256 balance);

    /**
     * @dev Returns the owner of the `tokenId` token.
     *
     * Requirements:
     *
     * - `tokenId` must exist.
     */
    function ownerOf(uint256 tokenId) external view returns (address owner);

    /**
     * @dev Safely transfers `tokenId` token from `from` to `to`.
     *
     * Requirements:
     *
     * - `from` cannot be the zero address.
     * - `to` cannot be the zero address.

#### `Transfer` 事件
```solidity
event Transfer(address indexed _from, address indexed _to, uint256 indexed _tokenId);
```
*必须*在转移任何 NFT 时发出，包括铸造和销毁。

当铸造代币时，`_from` 为零地址。
当销毁代币时，`_to` 为零地址。

#### `Approval` 事件
```solidity
event Approval(address indexed _owner, address indexed _approved, uint256 indexed _tokenId);
```
当 `approve(address _approved, uint256 _tokenId)` 函数成功执行时*必须*发出。

#### `ApprovalForAll` 事件
```solidity
event ApprovalForAll(address indexed _owner, address indexed _operator, bool _approved);
```
当 `setApprovalForAll(address _operator, bool _approved)` 函数成功执行时*必须*发出。

#### `balanceOf` 函数
```solidity
function balanceOf(address _owner) external view returns (uint256);
```
返回由 `_owner` 持有的代币数量。当 `_owner` 是零地址时，*必须*还原。

#### `ownerOf` 函数
```solidity
function ownerOf(uint256 _tokenId) external view returns (address);
```
在给定 `_tokenId` 的情况下，返回 NFT 的所有者。当 `_tokenId` 不存在时，*必须*还原。

#### `safeTransferFrom` 函数
```solidity
function safeTransferFrom(address _from, address _to, uint256 _tokenId, bytes data) external payable;
```
从地址 `_from` 将 `_tokenId` 代币转移到地址 `_to`

当满足以下条件时，此函数是*安全转移*：

*   当 `_to` 为合约地址时，此函数调用 `_to` 地址上的  `onERC721Received` （请参见下文）并且*必须*检查返回值，如果返回值是 `bytes4(keccak256("onERC721Received(address,address,uint256,bytes)"))`，则调用方可以执行交易。否则，*必须*还原交易。
*   当 `_to` 不是合约地址时，此函数 *必须* 像往常一样执行交易。
*   此函数 *必须* 在执行其他操作之前，检查消息调用者是否被授权转移代币 ID `_tokenId`。
*   此函数 *必须* 在所有权成功转移后发出 `Transfer` 事件。
*   如果 `_from` 地址不是当前 `_tokenId` 代币的所有者，*必须*还原。
*   如果 `_to` 地址是零地址，*必须*还原。
*   如果 `_tokenId` 无效，*必须*还原。
*   `data` 参数是附加的任意数据，没有要求。

#### `safeTransferFrom` 函数
```solidity
function safeTransferFrom(address _from, address _to, uint256 _tokenId) external payable;
```
从地址 `_from` 将 `_tokenId` 代币转移到地址 `_to`。此函数等效于
```solidity
safeTransferFrom(_from, _to, _tokenId, "");
```

当满足以下条件时，此函数是*安全转移*：

*   当 `_to` 为合约地址时，此函数调用 `_to` 地址上的  `onERC721Received` （请参见下文）并且*必须*检查返回值，如果返回值是 `bytes4(keccak256("onERC721Received(address,address,uint256,bytes)"))`，则调用方可以执行交易。否则，*必须*还原交易。
*   当 `_to` 不是合约地址时，此函数 *必须* 像往常一样执行交易。
*   此函数 *必须* 在执行其他操作之前，检查消息调用者是否被授权转移代币 ID `_tokenId`。
*   此函数 *必须* 在所有权成功转移后发出 `Transfer` 事件。
*   如果 `_from` 地址不是当前 `_tokenId` 代币的所有者，*必须*还原。
*   如果 `_to` 地址是零地址，*必须*还原。
*   如果 `_tokenId` 无效，*必须*还原。

#### `transferFrom` 函数
```solidity
function transferFrom(address _from, address _to, uint256 _tokenId) external payable;
```
从地址 `_from` 将 `_tokenId` 代币转移到地址 `_to`。

此函数 *必须* 在执行其他操作之前，检查消息调用者是否被授权转移代币 ID `_tokenId`。
此函数 *必须* 在所有权成功转移后发出 `Transfer` 事件。
如果 `_from` 地址不是当前 `_tokenId` 代币的所有者，*必须*还原。
如果 `_to` 地址是零地址，*必须*还原。
如果 `_tokenId` 无效，*必须*还原。

**注意：**强烈建议不要使用此函数，因为它不允许您在将 NFT 发送到合约时处理 NFT。最好使用 `safeTransferFrom` 函数，因为它会强制执行对接收合约的回调。

#### `approve` 函数
```solidity
function approve(address _approved, uint256 _tokenId) external payable;
```
允许 `_approved` 地址从调用者的地址中提取 `_tokenId` 代币。如果发生，*必须*触发 `Approval` 事件。如果调用者不是 `_tokenId` 的所有者，*必须*还原。

#### `setApprovalForAll` 函数
```solidity
function setApprovalForAll(address _operator, bool _approved) external;
```
批准或取消批准某个地址（`_operator`）代表消息的调用者管理所有代币。

当 `_approved` 为真时，该运算符可以管理消息调用者拥有的所有 NFT。另外，仅允许每个所有者有一个运算符。如果发生此类更改，*必须*触发 `ApprovalForAll` 事件。

#### `getApproved` 函数
```solidity
function getApproved(uint256 _tokenId) external view returns (address);
```
返回批准的地址以获取 `_tokenId` 代币。如果未批准任何内容或 `_tokenId` 无效，则返回零地址。

#### `isApprovedForAll` 函数
```solidity
function isApprovedForAll(address _owner, address _operator) external view returns (bool);
```
如果 `_operator` 被授权代表 `_owner` 管理所有 NFT，则返回 true，否则返回 false。

#### `onERC721Received` 函数
```solidity
function onERC721Received(address _operator, address _from, uint256 _tokenId, bytes _data) external returns(bytes4);
```

该挂钩*可以*在合约上实现，以便在 `safeTransferFrom`（上文）收到 ERC721 代币时通知它们。此挂钩在任何 ERC721 `safeTransferFrom` 调用之后调用，如果接收合约实现了 `IERC721Receiver`，则调用该合约。如果合格的接收器合约未实现此函数（即，它没有声明它）或返回意外值，则交易 *必须* 还原。

返回值*必须*是 `bytes4(keccak256("onERC721Received(address,address,uint256,bytes)"))`（即 `0x150b7a02`）。

## 原理

本建议不是设计一种全新的 NFT 协议。相反，设计的是一个最小的补充结构，可用于任何 NFT 合约，以便能够构建具有最大互操作性的平台。

## 向后兼容性

此 EIP 与任何先前的 EIP 不兼容。

## 安全考虑

需要认真考虑 `safeTransferFrom` 接口。如果接收地址是合约，并且该合约没有实现 `onERC721Received` 函数，则代币将永远锁定在该合约中。由于代币供应量会减少，这可能会造成意外的经济影响。作者敦促实现者提供一种方式来撤回错误的转移，或者选择一种更安全的方法。

实现此标准的合约 *必须* 采取预防措施以保护自己免受执行重入攻击的影响。

## 摘要

本提案定义了一个标准接口，允许用户使用 [ERC-721](https://eips.ethereum.org/EIPS/eip-721) 或 [ERC-1155](https://eips.ethereum.org/EIPS/eip-1155) NFT 作为以太坊账户。
该标准定义了智能合约如何识别和使用 NFT 作为账户，从而简化了用户体验并为新的应用程序打开了大门。

## 动机

以太坊账户的管理，特别是密钥的管理，通常是用户体验中复杂且令人生畏的部分。
用户通常需要依赖浏览器扩展、硬件钱包或其他密钥管理解决方案来安全地存储和管理他们的私钥，这可能很麻烦且容易出错。

相比之下，NFT 由于其在数字艺术、收藏品和游戏中的普及，已经获得了广泛的认可和采用。
许多用户已经熟悉购买、出售和交易 NFT 的概念。

通过允许用户使用 NFT 作为以太坊账户，我们可以利用 NFT 的熟悉度和易用性来简化用户体验并使更多人更容易访问以太坊。

## 规范

### 必须

以下关键词“必须”、“不得”、“必需”、“应”、“不应”、“应该”、“不应该”、“推荐”、“可能”和“可选”在本文件中应按 RFC 2119 中的描述进行解释。

### 定义

1.  **NFT 账户合约**：实现 `IERC7684` 接口的合约。
2.  **NFT 账户**：用作账户的特定 NFT。
3.  **账户合约**：与 NFT 账户交互的合约。

### IERC7684 接口

```solidity
pragma solidity ^0.8.0;

/**
 * @title IERC7684
 * @dev Interface for ERC-7684.
 */
interface IERC7684 {
    /**
     * @dev Returns the address associated with the given NFT.
     * @param tokenContract The address of the NFT contract.
     * @param tokenId The ID of the NFT.
     * @return The address associated with the NFT.
     */
    function account(address tokenContract, uint256 tokenId) external view returns (address);

    /**
     * @dev Returns the code hash of the account associated with the given NFT.
     * @param tokenContract The address of the NFT contract.
     * @param tokenId The ID of the NFT.
     * @return The code hash of the account associated with the NFT.
     */
    function accountCodeHash(address tokenContract, uint256 tokenId) external view returns (bytes32);
}
```

### 函数定义

#### `account(address tokenContract, uint256 tokenId) external view returns (address)`

*   `tokenContract`: NFT 合约的地址。
*   `tokenId`: NFT 的 ID。

`account` 函数必须返回与给定 NFT 关联的地址。
如果给定的 NFT 未与帐户关联，则该函数必须返回零地址 (`address(0)`)。

#### `accountCodeHash(address tokenContract, uint256 tokenId) external view returns (bytes32)`

*   `tokenContract`: NFT 合约的地址。
*   `tokenId`: NFT 的 ID。

`accountCodeHash` 函数必须返回与给定 NFT 关联的帐户的代码哈希。
如果给定的 NFT 未与帐户关联，则该函数必须返回 `bytes32(0)`。

### 行为

1.  **账户合约兼容性**：
    希望支持 NFT 账户的合约必须使用 `IERC7684` 接口来确定地址是否为 NFT 账户。

2.  **使用 NFT 账户发送交易**：
    发送交易时，发件人可以是符合 `IERC7684` 接口的 NFT 的地址。
    交易的签名必须由与 NFT 账户关联的私钥持有者授权。

3.  **部署合约**：
    使用 NFT 账户部署合约要求 `tokenContract` 和 `tokenId` 在部署交易的 `initCode` 中进行编码。
    这允许 `CREATE` 和 `CREATE2` 操作码使用 NFT 账户作为部署者。

### 示例

```solidity
pragma solidity ^0.8.0;

import "./IERC7684.sol";

contract MyContract {
    IERC7684 public immutable nftAccountContract;

    constructor(IERC7684 _nftAccountContract) {
        nftAccountContract = _nftAccountContract;
    }

    function isNFTAccount(address _address, address _tokenContract, uint256 _tokenId) external view returns (bool) {
        return nftAccountContract.account(_tokenContract, _tokenId) == _address;
    }
}
```

在此示例中，`MyContract` 检查给定地址是否为 NFT 账户。
它通过调用 `nftAccountContract` 的 `account` 函数来实现这一点，传递 token 合约地址和 token ID。
如果 `account` 函数返回与给定地址匹配的地址，则该函数返回 `true`，表明该地址是 NFT 帐户。

### 部署合约

```typescript
const nftAddress = "0x...";
const tokenId = 1;
const nftAccount = await nftAccountContract.account(nftAddress, tokenId);

//  发送资金到 NFT 账户
await signer.sendTransaction({
  to: nftAccount,
  value: ethers.utils.parseEther("1.0")
});

//  部署合约
const MyContract = await ethers.getContractFactory("MyContract");
const constructorArgs = [nftAccountContract.address];
const factory = new ethers.ContractFactory(MyContract.interface, MyContract.bytecode, signer);
const contract = await factory.deploy(...constructorArgs, {
    gasLimit: 10000000,
    customData: {
        nftAddress: nftAddress,
        tokenId: tokenId
    }
});
```

在此示例中，我们展示了如何将资金发送到 NFT 账户并从 NFT 账户部署合约。
要部署合约，我们需要在部署交易的 `customData` 字段中传递 `nftAddress` 和 `tokenId`。

## 原理

本提案旨在提供一种标准化的方法来使用 NFT 作为以太坊账户，同时最大限度地提高灵活性和兼容性。

## 向后兼容性

本提案与现有的以太坊标准和协议完全向后兼容。
它不引入任何可能破坏现有应用程序或合约的新规则或要求。

## 安全考虑

使用 NFT 作为帐户引入了以下安全考虑：

1.  **NFT 所有者的控制**：
    与 NFT 关联的帐户的安全性取决于 NFT 所有者的安全性。
    如果 NFT 的所有者丢失了他们的私钥或他们的 NFT 被盗，他们也将失去对关联帐户的控制权。

2.  **NFT 转移的影响**：
    当 NFT 从一个所有者转移到另一个所有者时，与该 NFT 关联的帐户的控制权也会转移到新的所有者。
    在转移 NFT 之前，用户应注意这一点。

3.  **gas 成本**：
    与使用 NFT 作为帐户相关的 gas 成本可能高于使用传统以太坊帐户。
    这是因为使用 NFT 帐户需要额外的链上操作。

## 摘要

本 EIP 提出引入一个新的操作码 `SHAREDOWNER`，该操作码接受存储槽、起始地址和地址计数作为参数。如果存储槽的值等于从起始地址开始的、计数数量的连续地址的 Keccak-256 哈希值，则操作码返回 `1`；否则返回 `0`。

## 动机

帐户抽象（AA）已成为以太坊生态系统中日益普及的领域。这种普及带来了一些挑战，例如需要新的方法来验证交易是否由智能合约钱包的所有者发起。

目前，通过合约逻辑强制执行所有权，这可能会导致更高的 gas 成本和更大的复杂性。提供一种更高效、更标准化的链上所有权验证方法将对 AA 钱包及其他领域有益。

引入 `SHAREDOWNER` 操作码为合约提供了一种原生方式来验证一组地址是否控制了给定的存储槽。这可以简化 AA 钱包的逻辑，降低 gas 成本，并启用新的用例。

## 规范

### 参数

| 参数    | 类型   | 描述                                                                 |
| :------ | :----- | :------------------------------------------------------------------- |
| 存储槽  | `uint256` | 要检查的存储槽。                                                     |
| 起始地址 | `uint256` | 从中加载连续地址的起始内存位置。                                           |
| 地址计数 | `uint256` | 要考虑的地址数量。                                                       |

### 逻辑

`SHAREDOWNER` 操作码应执行以下步骤：

1.  从内存中加载 `addressCount` 个地址，从 `baseAddress` 开始，并将结果连接成一个字节数组。
2.  计算该字节数组的 Keccak-256 哈希值。
3.  如果该哈希值等于 `存储槽` 的值，则返回 `1`。
4.  否则，返回 `0`。

### 公式

`SHAREDOWNER(slot, baseAddress, addressCount) = keccak256(address_1 || address_2 || ... || address_n) == storage[slot]`

其中：

*   `slot` 是要检查的存储槽。
*   `baseAddress` 是内存中地址序列的起始位置。
*   `addressCount` 是要考虑的地址数量。
*   `address_i` 是从 `baseAddress + (i * 20)` 加载的地址。
*   `storage[slot]` 是 `slot` 处存储槽的值。

### Gas 成本

`SHAREDOWNER` 操作码的 gas 成本应为：`300 + (addressCount * 50)` gas。

### 操作码

| 操作码 | 名称          |
| :----- | :------------ |
| 0x??   | `SHAREDOWNER` |

## 原理

### 替代方案

在没有 `SHAREDOWNER` 操作码的情况下，合约必须通过加载每个地址、连接它们并计算 Keccak-256 哈希值来手动验证所有权。这种方法效率较低，并且会消耗更多的 gas。

### Gas 成本注意事项

`SHAREDOWNER` 操作码的 gas 成本被设计为与手动验证所有权的成本具有竞争力。`300` gas 的基本成本是为了补偿操作码本身的开销，而 `addressCount * 50` gas 的每地址成本是为了补偿加载和哈希地址的成本。

### 安全注意事项

`SHAREDOWNER` 操作码不会引入任何新的安全风险。它只是提供了一种更高效的方式来验证链上所有权。但是，重要的是要注意，`SHAREDOWNER` 操作码只能用于验证存储槽中存储的地址的哈希值。它不能用于验证其他类型的数据。

## 向后兼容性

`SHAREDOWNER` 操作码与现有的以太坊合约向后兼容。它仅引入了一个新的操作码，该操作码不会影响现有合约的行为。

## 测试用例

以下是一些 `SHAREDOWNER` 操作码的测试用例：

1.  存储槽的值等于单地址的 Keccak-256 哈希值。
2.  存储槽的值等于多个地址的 Keccak-256 哈希值。
3.  存储槽的值不等于地址的 Keccak-256 哈希值。
4.  `addressCount` 为零。
5.  `addressCount` 非常大，导致 gas 耗尽。

## 实现

`SHAREDOWNER` 操作码的实现将需要在以太坊虚拟机（EVM）中添加一个新的操作码。该操作码应执行以下步骤：

1.  从堆栈中加载 `slot`、`baseAddress` 和 `addressCount` 参数。
2.  从内存中加载 `addressCount` 个地址，从 `baseAddress` 开始，并将结果连接成一个字节数组。
3.  计算该字节数组的 Keccak-256 哈希值。
4.  如果该哈希值等于 `slot` 处存储槽的值，则将 `1` 推送到堆栈上。
5.  否则，将 `0` 推送到堆栈上。

## 安全注意事项

关于引入新的 `SHAREDOWNER` 操作码，有几个需要考虑的安全问题：

1.  **Gas 成本操纵：** 恶意合约可能会尝试操纵 `addressCount` 参数以导致 gas 耗尽。为了缓解这种情况，建议设置 `addressCount` 的最大值，或者确保 gas 成本与地址数量成比例，以防止滥用。

2.  **冲突风险：** Keccak-256 哈希算法被认为可以抵抗冲突，但仍然存在两个不同的地址集生成相同哈希值的极小可能性。合约应意识到这种风险，并考虑在所有权验证过程中实现额外的检查，以最大程度地降低冲突的影响。

3.  **内存利用漏洞：** `SHAREDOWNER` 操作码从内存中读取地址。恶意合约可能会尝试通过提供指向恶意或不可访问内存位置的 `baseAddress` 来利用此功能，从而可能导致错误或意外行为。为了防止这种情况，应采取适当的内存边界检查和验证。

4.  **重放攻击：** 如果合约依赖于 `SHAREDOWNER` 操作码来授权敏感操作，那么必须采取措施来防止重放攻击。重放攻击是指恶意行为者重复使用有效交易以未经授权地执行操作的情况。实施 nonce 或其他时间敏感机制可以缓解这种风险。

5.  **组合性风险：** 当 `SHAREDOWNER` 操作码与其他合约或协议结合使用时，可能会出现组合性风险。开发人员应仔细分析集成的影响，并确保与其他组件的兼容性，以避免意外的安全漏洞。

6.  **智能合约漏洞：** 与任何智能合约实现一样，都存在代码中引入漏洞的风险。彻底的审核、正式验证和最佳实践应遵循，以最大程度地降低利用与 `SHAREDOWNER` 操作码相关的智能合约的风险。

通过解决这些安全问题并在实现中使用适当的缓解措施，`SHAREDOWNER` 操作码可以安全有效地用于以太坊生态系统中，从而增强所有权验证过程并为各种应用程序提供便利。
