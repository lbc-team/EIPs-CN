## 简单总结
一个构建区块 `access_list` 并在区块头中包含其指纹 `AccessListRoot` 的提案。

## 摘要
[EIP-2929](./eip-2929.md)/[EIP-2930](./eip-2930.md) 的核心在于规范化交易对数据/存储访问的（低）gas 成本，并提供（和鼓励）一种新的交易类型格式：
```
0x01 || rlp([chainId, nonce, gasPrice, gasLimit, to, value, data, access_list, yParity, senderR, senderS])
```
它预先声明了 `access_list`，其中 `access_list` 是 `[[{20 bytes}, [{32 bytes}...]]...]` 的 `AccessedAddress=> AccessedStorageKeys` 映射。

这些预先*声明*的首次*访问*将以折扣价（大约 ~`10%`）收费，而此列表之外的首次访问将以更高的价格收费。原因是预先访问声明提供了一种在执行事务时*预加载/优化/批量*加载这些位置的方法。
这无意中导致生成了事务 `access_list`，该列表具有事务进行的所有（首次）访问（声明或未声明）。
本提案旨在整理 **区块** `access_list` 文档中所有事务的这些 *事务* `access_list`，并在区块头中包含其 *指纹*。

## 动机
整理 **区块** 的 `access_list` 中所有事务的 *事务* `access_list` 的动机是拥有区块的 *访问索引*，具有以下优点：
1. 通过启用访问和执行的 *偏序* 构造来优化/并行化/缓存预热区块执行/验证（提示：此 *poset* 中的 *链* 可以并行化）。
2. 通过与地址子集相关的 *轻同步* 或 *快速同步* 协议，能够进行部分检查和获取/服务区块数据/状态。
3. 此列表的未来扩展，可以用作捆绑、服务和获取 *无状态* 协议的见证数据的索引。

## 规范
区块 `access_list` 表示：
```
Set [ 
    AccessedAddress, 
    List [AccessedStorageKeys] , 
    Set  [ AccessedInBlockTransactionNumber, List [ AccessedStorageKeys ]]  
]
```
这种 `access_list` 的**规范**构造如下所述。

### 规范区块访问列表
`access_list` 定义为由多个 `access_list_entry` 元素组成：
```
access_list   :=  [access_list_entry, ...]
```

`access_list_entry` 是一个 3 元组：
* address
* 整个区块中访问的地址的排序后的存储键列表
* 排序后的 2 元组列表：
    * 访问了地址或其任何存储键的交易索引
    * 排序后的已访问存储键列表

```
access_list                 := [access_list_entry, ...]
access_list_entry           := [address, storage_keys, accesses_by_txn_index]
address                     := bytes20
accesses_by_txn_index       := [txn_index_and_keys, ...]
txn_index_and_keys          := [txn_index, storage_keys]
txn_index                   := uint64  # 或 uint256 或其他
storage_keys                := [storage_key, ...]
storage_key                 := bytes32
```

上述额外的排序规则是：
* `access_list` 按 `address` 排序
* `storage_keys` 已排序
* `accesses_by_txn_index` 按 `txn_index` 排序

上述的附加验证规则是：
* 每个唯一的 `address` 在 `access_list` 中最多只能出现一次
* 每个 `storage_key` 在 `storage_keys` 中最多只能出现一次
* 每个 `txn_index` 在 `txn_index_and_keys` 中最多只能出现一次

所有排序都按升序排列。

### AccessListRoot
`AccessListRoot` 是规范 `access_list` 以及构造类型（`sha256`）和序列化类型（`json`）的 URN *类似*编码 `Hash/Commitment`，即
```
AccessListRoot := "urn:sha256:json:0x${ SHA256( access_list.toJSONString('utf8') ).toHexString() }"
```
其中 `0x${ SHA256 (...)...}` 是 `SHA256` 哈希的 `32` 字节十六进制字符串，如前导 `0x` 所示。

### 额外的区块验证
验证新区块需要额外的验证检查，即区块的 `AccessListRoot` 与使用 `AccessListRoot` URN 定义的构造执行区块生成的 `AccessListRoot` 匹配。

## 理由
### 规范 `access_list` 的排序
它被指定为按字典顺序或整数排序（如果适用且已指定）进行排序。 考虑了关于访问时间的排序，但似乎没有以增加实现复杂性和簿记成本为代价提供任何额外的好处。

### *访问列表根*
生成 `AccessListRoot` 是为了防止任何 *griefing* 攻击，因此需要将其包含在 *区块头* 中（并进行验证）。
尽管当前指定 `AccessListRoot` 是规范 `access_list` 的简单 `sha256` 哈希，但考虑其他构造会很有益处
* 树结构（`merkle`/`verkle`）。 它会稍微贵一些，但可以部分下载、检查和验证 `access_list`。
* 也可以生成普通的 `kate` 承诺来实现此部分功能，并且建议这样做，因为验证访问列表块的部分提取非常简单。

同样，`access_list` 的序列化当前被指定为普通的 `JSON String` 转储，并且这些参数可能因构造而异，但为了简单起见，它始终可以进行 `sha256` 哈希以获得一致的 `32` 字节十六进制字符串根。

因此，此 AccessListRoot 可以演变为 `urn:merkle:ssz:...` 或 `urn:kate:...` 或任何其他根据要求的方案。 拥有作为 URN *类似* 结构的 `AccessListRoot` 的想法是为了能够在不影响区块结构的情况下升级到这些路径。

### `access_list` 的未来扩展
我们可以扩展区块 `access_list` 的概念以包括见证：
```
access_list := Set[ 
    Address,
    List [ AddressWitnesses ],
    Set  [ AccessedStorageKey, List [ StorageKeyWitnesses] ],        
    Set  [ AccessedInBlockTransactionNumber, List [ AccessedStorageKeys ] ]
]
```
然后定义构建指纹的规范规范。
这将允许通往部分或完全无状态的增量路径，在这种情况下，使用此 `access_list` 捆绑/请求 **见证** 会很容易。

## 向后兼容性
额外的区块验证仅在 EIP 生效的区块号之后是强制性的，但客户端仍然可以提供一种方法来生成（并可能存储）此访问列表（通过 `JSON/RPC` API）。 但是，这是可选的并且取决于客户端。

## 安全考虑
此更改不会导致任何已知的安全问题。
