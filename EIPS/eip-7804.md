## 摘要

本提案定义了一种机制，允许验证者使用新的执行请求类型 (0x03) 更新其提款凭证。
该请求允许更改执行地址和提款凭证前缀（0x01 或 0x02）。

## 动机

当 Capella 中引入了将验证者的 BLS 提款凭证更新为执行地址的功能时，最常见的问题之一是关于
允许未来更改提款凭证。
无论是出于安全考虑（例如，凭证轮换），还是为了允许处理提款的替代方法（例如，将合约地址作为凭证）。
没有添加此选项的主要原因是实现
执行层和共识层之间的这种通信通道很复杂（基于 Eth1 网桥的经验）。

在 Electra 中，协议已通过执行请求（存款、提款和
合并）进行了升级，以及用于通用执行请求的机制
[EIP-7685](./eip-7685.md)，降低了添加
来自执行层的新请求的复杂性。

在执行层创建的执行请求的引入，
为如何管理验证者开辟了可能性。
执行请求可以通过智能合约创建，从而允许探索去中心化和链上机制。
这也意味着验证者将能够在执行和复合提款凭证之间移动（遵循总质押金额的正确流失）。

为了使执行请求在共识层中获得授权，验证者的提款
凭证必须与在 EVM 上处理交易时 `msg.caller` 的凭证相同。
因此，验证者的提款凭证必须与智能合约的地址相同
创建请求（而不是交易发送者的凭证的地址），或者合约
需要使用 `DELEGATECALL` 来确保调用者地址与
验证者的提款凭证中的地址匹配。
已经将合约地址设置为其提款凭证的验证者应该能够
更新他们的合约以满足此需求（假设他们有一个
可更新的合约）。

对于现有验证者，他们的提款凭证存在问题
设置为 EOA 帐户，他们将永远无法使用智能合约
用于创建执行请求，因为当前设计不允许这些
凭证永远被更改。

允许验证者更新其提款凭证意味着他们可以选择加入
并退出管理其验证者的不同方案和策略，从而促进
实验和创新。
今天，唯一的替代方法是退出验证者并创建一个新的
具有不同提款凭证的验证者。

### 执行层

* **`FORK_BLOCK`** -- 区块链中 `timestamp` 大于或等于 `FORK_TIMESTAMP` 的第一个区块。

#### 提款凭证更新请求操作

新的提款凭证更新请求操作是类型为 `0x03` 的 [EIP-7685](./eip-7685.md) 请求
并且包含以下字段：

1. `pubkey`: `Bytes48`
2. `old_address`: `Bytes20`
3. `new_address`: `Bytes20`

提款凭证更新请求的 [EIP-7685](./eip-7685.md) 编码计算如下。

```python
request_type = WITHDRAWAL_CREDENTIALS_UPDATE_REQUEST_TYPE
request_data = read_withdrawal_credential_update_requests()
```

#### 提款凭证更新请求合约

该合约与其他用于存款、提款和合并的执行请求合约类似。
该合约有三个不同的代码路径，可以概括为以下几个方面：

1. 添加请求 - 需要一个 `68` 字节的输入，验证者的公钥与提款凭证的新地址连接。
2. 获取多余的请求 - 如果输入长度为零，则返回当前的多余请求计数。
3. 系统进程 - 如果由系统地址调用，则从队列中弹出当前区块的提款凭证更新请求。

#### 区块处理

在处理任何 `block.timestamp >= FORK_TIMESTAMP` 的执行区块结束时（即，在处理所有交易之后以及在执行区块主体请求验证之后），客户端软件 **必须** 调用作为 `SYSTEM_ADDRESS` 的合约和空输入数据，以触发系统子例程执行。根据 [EIP-7685](./eip-7685.md)，该响应应被视为一种新的请求类型 (0x03)。

#### 区块验证

EL 必须检查执行区块标头中的承诺哈希是否与 CL 在
验证执行区块时发送的执行请求列表的哈希匹配（包括任何新定义的类型 0x03 的请求）。

    validator_pubkey: BLSPubkey
    old_address: ExecutionAddress  # 请求合约会将此设置为 msg.caller

```python
def process_withdrawal_credential_update_request(state: BeaconState, withdrawal_credentials_update_requests: WithdrawalCredentialUpdateRequest) -> None:
    validator_pubkeys = [v.pubkey for v in state.validators]
    # 验证 pubkey 是否存在
    request_pubkey = withdrawal_credentials_update_requests.validator_pubkey
    if request_pubkey not in validator_pubkeys:
        return
    index = ValidatorIndex(validator_pubkeys.index(request_pubkey))
    validator = state.validators[index]

    # 验证提款凭证
    has_correct_credential = has_execution_withdrawal_credential(validator)
    is_correct_old_address = (
        validator.withdrawal_credentials[12:] == withdrawal_credentials_update_requests.old_address
    )
    if not (has_correct_credential and is_correct_old_address):
        return

    credential_type = withdrawal_credentials_update_requests.type
    is_eth1_type = credential_type == ETH1_ADDRESS_WITHDRAWAL_PREFIX
    is_compounding_type = credential_type == COMPOUNDING_WITHDRAWAL_PREFIX
    # 验证有效类型
    if not (is_eth1_type or is_compounding_type):
        return;

    update_withdrawal_credentials(state, index, credential_type, withdrawal_credentials_update_requests.new_address)
```

```python
def update_withdrawal_credentials(state: BeaconState, index: ValidatorIndex, new_credential_type: Bytes1, new_withdrawal_credentials: ExecutionAddress) -> None:
    old_credential_type = validator.withdrawal_credentials[:1]

    validator = state.validators[index]
    validator.withdrawal_credentials = (
        new_credential_type
        + b'\x00' * 11
        + new_withdrawal_credentials
    )

    # 如果从 0x01 移动到 0x02

## 安全考虑

所有权是基于对提款凭证帐户的控制来定义的，无论是私钥（对于 EOA 帐户）还是控制
地址设置为提款凭证的智能合约。因此，允许更新不应带来任何安全影响。
