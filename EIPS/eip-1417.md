## 简单总结

用于 EIP-1261 (MVT) 的投票的标准接口。

## 摘要

以下标准允许为投票实现一个标准 API，以与 MVT 一起使用（参考[EIP-1261](./eip-1261.md)）。该标准提供了投票、取消投票、统计投票、获取选民投票率等基本功能。投票标准试图通过将投票分解为 4 个关键组成部分来实现区块链投票的模块化：选民基础资格、投票权重计算、投票后果和投票统计。通过为具有不同构建块的投票创建通用接口，投票标准可以创建交互式前端应用程序，这些应用程序可以无缝地从投票合约获取数据，从而提高区块链上共识和决策的透明度。

我们考虑了将投票与 MVT 结合使用，因为 MVT 充当一种权限机制。手动权限控制投票允许投票权重函数呈现多种形式。因此，选民基础函数对投票发送者执行多项逻辑检查，以确认他们是某个实体或实体组合的成员（请参阅 EIP 1261）。对于投票性质的规范，我们定义了投票权重函数。投票权重函数决定了每个选民将获得多少投票份额，这可以基于多个标准，其中一些标准已在本文中列出。某些类型的投票会对选民施加某些后果，例如，投票可能要求选民锁定一定数量的代币，或要求选民支付少量费用。这些链上后果可以编码到投票标准的后果模块中。最后，最后一个模块是添加投票的地方。每当相关时，都会更新每个候选人的选票，具体取决于投票价值，以及相应的 NoV 计数（选民人数）。此模块对于大多数投票来说是通用的，并且是最直接的。投票可能有时限，即具有结束时间，在此之后不会记录任何投票，也可能没有时限，因此没有结束时间。以下是一些利用投票标准灵活性的特定投票示例，并且有可能提出其他几个示例：

- 多数投票：最简单的投票形式是当您希望所有符合条件的选民每人拥有一票时。这是最容易编码的，因为投票权重为 1，并且没有投票后果。此处唯一相关的模块是选民基础，它可以通过一个或多个 MVT 合约进行分类。
- 代币比例投票：实际上，这种投票可以在不使用选民基础函数的情况下实现，因为具有代币比例的投票权重函数会自动排除不持有适当 ERC - 20/ ERC - 777 代币的地址。但是，可以利用选民基础函数来进一步授权系统，并且仅向固定子集的代币持有者授予投票权。
- 有上限的代币比例投票：这是上一个示例的修改版本，其中每个选民仅在达到一定代币持有量限制之前获得比例投票份额。超过该限制后，持有更多代币不会增加更多投票份额。此格式有效地利用了选民基础模块，通过允许管理员控制哪些地址可以投票来防止人们将他们的代币分散到多个地址。
- 委托投票：某些投票可能允许选民将其投票委托给其他选民。这被称为委托投票或液体民主。对于此类投票，需要复杂的投票权重函数，并且还需要有关选民基础的数据结构。此处投票的后果是用户无法委托，而委托的后果是用户无法投票。投票的示例实现包含此投票方案的示例。
- 基于 Karma 的投票：某种形式的投票可能基于数字尊重程度的权重。这种数字尊重就像选民基础的一名成员对另一成员的简单赞成票。映射的映射以及适当的投票权重函数可以实现此目的。示例实现有一个示例。
- 二次投票：一种系统，其中每次投票都与费用相关联，并且费用与选民想要的投票权重的平方成正比。这可以通过应用基于交易消息的投票权重，然后在投票结果模块中收取费用来设计。

投票标准旨在成为一个智能合约标准，使投票部署灵活、透明和可访问。

## 动机

标准接口允许任何用户或应用程序与以太坊上的任何投票合约一起使用。我们为简单的 ERC-1417 智能合约提供支持。其他应用程序将在下面讨论。

此标准的灵感来自于区块链领域缺乏治理工具。每当进行共识收集活动时，都会有人继续部署某种投票，并且没有标准的软件来访问投票上的数据。对于不是开发人员的最终用户来说，这是一个真正的问题。对于不了解区块链的普通用户来说，可能完全透明的投票似乎完全不透明。为了让开发人员构建用于交互和访问投票数据的应用程序，并让投票部署者拥有现成的应用程序级别支持，必须对投票接口进行标准化。

这种认识是在对 DAICO 进行市场研究时发生的。有史以来第一次 DAICO，Abyss，拥有远非最佳的用户体验，并且透明度极低。从那时起，我们一直在研究投票标准。在此过程中，我们遇到了投票标准 EIP 1202，并且发现那里的讨论已经与我们的想法相去甚远，以至于发布单独的提案是有意义的。投票标准带来的一些好处 - EIP 1417 旨在提供一些额外的好处。

1. 模块化：EIP 1417 根据功能将投票标准中的代码模块化为 4 个主要构建块。这些是：选民基础逻辑、投票权重计算、投票后果处理和统计模块。这使得开发人员可以轻松地更改投票的某些部分而不会中断其他部分，并且还有助于人们更好地理解他人以相同格式编写的代码。

2. 授权：授权是投票的一个重要方面，并且到目前为止在区块链上的大多数投票提案中都缺失了。由于某种原因，大多数基于区块链的投票似乎都认为持有代币是授权投票的唯一方式。然而，这阻碍了灵活性，因此我们的投票标准正在利用 EIP 1261 来清除授权障碍。它不仅允许在投票权重方面创造更具创意的投票结构，而且还通过允许开发人员组合多个实体并从实体读取属性来提高授权的灵活性。

3. 灵活性：投票标准的投票权重模块可以有效地用于设计各种功能不同的投票合约，这些合约适用于不同的环境。一些示例包括二次投票、Karma 投票、委托投票、基于代币的投票和一人一票系统。这些方案之所以可行，是因为选民基础的创建和投票权重计算是分开的。

4. NoV 计数：一些加权投票一直在努力提供适当的透明度，因为它们仅显示最终结果而没有足够的粒度。这是因为他们不存储已投票给每个提案的选民人数，而仅存储每个选项的累积总投票数。EIP 1417 通过额外记录每个提案中的选民人数 (NoV) 来解决此问题。此 NoV 计数在一人一票的情况下是多余的，但在其他地方，它有助于弄清权力的集中程度。这确保了可以在更大程度上追踪恶意方。

5. 事件日志记录：投票标准会在成功投票、未成功投票和成功取消投票期间记录一个事件。这样做是为了在恶意管理员删除真实成员或添加虚假成员的情况下，社区可以构建工具来执行高级审计并模拟在没有恶意攻击的情况下的结果。此类高级功能在大多数投票中完全不存在，因此很难调查此类投票。

6. Pollscan.io：Electus 基金会正在开发一个基于 Web 的应用程序，用于访问和交互区块链上的投票数据，它将在未来几个月内部署在域名 www.pollscan.io 上。

总而言之，我们很高兴与社区分享我们的提案，并在此领域内听取建议。

### 好处

1. 在标准化的投票接口之上构建应用程序 (pollscan.io) 可以提高透明度，并鼓励更多的 DAO/DAICO 在治理方面负责任地行事
2. 创建 Action 合约，这些合约根据投票结果以编程方式采取行动
3. 允许与代 [ERC-20](./eip-20.md) 或 (./eip-777.md)) 等币标准和 [EIP-1261](./eip-1261.md) 等成员标准兼容
4. 灵活性允许各种投票方案，包括但不限于现代方案，例如 PLCR 投票

### 用例：

投票在集体决策的任何环境中都很有用，包括但不限于：

1. 管理公共资源，如池塘、游乐场、街道等
2. 以透明的共识驱动方式维持财政政策

## 规范

本文档中的关键词“必须”、“不得”、“必需”、“应”、“不应”、“应该”、“不应该”、“推荐”、“可能”和“可选”应按照 RFC 2119 中的描述进行解释。

**每个符合 ERC-1417 的合约都必须实现 `ERC1417` 和 `ERC165` 接口**（受以下“注意事项”的约束）：

```solidity
/// @title ERC-1417 投票标准
/// @dev 请参阅 https://github.com/ethereum/EIPs/blob/master/EIPS/eip-1417.md
///  注意：此接口的 ERC-165 标识符为 0x4fad898b。
interface IPoll {
    /// @dev 当有人试图在没有权限的情况下投票时，会发出此消息。用于审计目的。
    ///  例如：为了防止管理员撤销权限；计算如果他们没有被删除的结果。
    /// @param _from 尝试投票的用户
    /// @param _to 他投票的提案的索引
    /// @param voteWeight 他的投票权重
    event TriedToVote(address indexed _from, uint8 indexed _to, uint voteWeight);

    /// @dev 当有人成功投票时，会发出此消息
    /// @param _from 成功投票的用户
    /// @param _to 他投票的提案的索引
    /// @param voteWeight 他的投票权重
    event CastVote(address indexed _from, uint8 indexed _to, uint voteWeight);

    /// @dev 当有人撤销他的投票时，会发出此消息
    /// @param _from 成功取消投票的用户
    /// @param _to 他取消投票的提案的索引
    /// @param voteWeight 他的投票权重
    event RevokedVote(address indexed _from, uint8 indexed _to, uint voteWeight);

    /// @notice 处理投票逻辑
    /// @dev 更新有关投票的适当数据结构。
    ///  存储针对用户的 proposalId，以便可以取消投票
    /// @param _proposalId 提案数组中提案的索引
    function vote(uint8 _proposalId) external;

    /// @notice 处理取消投票逻辑
    /// @dev 更新有关取消投票的适当数据结构
    function revokeVote() external;

    /// @notice 获取提案名称
    /// @dev 将提案计数限制为 32（出于实际原因），循环并生成提案列表
    /// @return 提案名称列表
    function getProposals() external view returns (bytes32[]);

    /// @notice 返回一个布尔值，指定用户是否可以投票
    /// @dev 实现逻辑以启用检查以确定用户是否可以投票
    ///  如果使用 eip-1261，请使用协议地址和接口 (IERC1261) 以启用使用属性进行检查
    /// @param _to 可以投票/不允许投票的人
    /// @return 布尔值，指示用户是否可以投票
    function canVote(address _to) external view returns (bool);

    /// @notice 获取 proposalId 的投票权重
    /// @dev 返回提案的当前累积投票权重
    /// @param _proposalId 提案数组中提案的索引
    /// @return 指定提案的累积投票权重
    function getVoteTally(uint _proposalId) external view returns (uint);

    /// @notice 获取投票给该提案的选民人数
    /// @dev 使用结构来跟踪 voteWeights 和 voterCount
    /// @param _proposalId 提案数组中提案的索引
    /// @return 投票给指定提案的人的选民人数
    function getVoterCount(uint _proposalId) external view returns (uint);

    /// @notice 计算与人 `_to` 相关的投票权重
    /// @dev 使用适当的逻辑来确定个人的投票权重
    ///  对于示例实现，请参阅 eip 的末尾
    /// @param _to 投票权重正在计算的人
    /// @return 个人的投票权重
    function calculateVoteWeight(address _to) external view returns (uint);

    /// @notice 获取当前领先的提案
    /// @dev 计算当前领先的提案
    ///  出于实际原因，将提案计数限制为 32。
    /// @return 领先提案的索引
    function winningProposal() external view returns (uint8);

    /// @notice 获取投票的名称，例如：“2018 年秋季的管理员选举”
    /// @dev 在投票的构造函数中设置名称
    /// @return 投票的名称
    function getName() external view returns (bytes32);

    /// @notice 获取投票的类型，例如：代币 (XYZ) 加权投票
    /// @dev 在投票的构造函数中设置投票类型
    /// @return 投票的类型
    function getPollType() external view returns (bytes32);

    /// @notice 获取要在投票的 `canVote` 函数中使用的逻辑
    ///  例如：“XYZ 代币 | 美国和中国（erc-1261 中的属性）| 开发人员（erc-1261 中的属性）”
    /// @dev 在投票的构造函数中设置 Voterbase 逻辑
    /// @return 选民基础逻辑
    function getVoterBaseLogic() external view returns (bytes32);

    /// @notice 获取投票的开始时间
    /// @dev 在投票的构造函数中将开始时间设置为 Unix 标准时间
    /// @return 开始时间为 Unix 标准时间
    function getStartTime() external view returns (uint);

    /// @notice 获取投票的结束时间
    /// @dev 在投票的构造函数中将结束时间设置为 Unix 时间，或者在构造函数中指定持续时间
    /// @return 结束时间为 Unix 标准时间
    function getEndTime() external view returns (uint);

    /// @notice 返回用于授权目的的实体地址列表 (eip-1261)。
    /// @dev 地址列表可以与 IERC1261 接口一起使用，以定义 `canVote()` 函数中的逻辑
    /// @return 实体的地址列表
    function getProtocolAddresses() external view returns (address[]);

    /// @notice 获取针对所有提案的投票权重
    /// @dev 将提案计数限制为 32（出于实际原因），循环并生成投票统计列表
    /// @return 针对所有提案的投票权重列表
    function getVoteTallies() external view returns (uint[]);

    /// @notice 获取投票反对所有提案的人数
    /// @dev 将提案计数限制为 32（出于实际原因），循环并生成投票计数列表
    /// @return 针对所有提案的选民计数列表
    function getVoterCounts() external view returns (uint[]);

    /// @notice 对于单个提案投票，返回总选民基础计数。
    ///  对于多个提案投票，返回针对所有提案的总投票权重
    ///  用于计算每个提案的百分比
    /// @dev 将提案计数限制为 32（出于实际原因），循环并生成选民基础分母
    /// @return 一个整数，指定上述金额
    function getVoterBaseDenominator() external view returns (uint);
}
```

### 注意事项

0.4.24 Solidity 接口语法不足以记录 ERC-1417 标准。符合 ERC-1417 的合约还必须遵守以下规定：

- Solidity 问题 #3412：上述接口包括每个函数的显式可变性保证。可变性保证按从弱到强的顺序排列：`payable`、隐式 nonpayable、`view` 和 `pure`。您的实现必须满足此接口中的可变性保证，您可以满足更强的保证。例如，此接口中的 `payable` 函数可以在您的合约中实现为 nonpayble（未指定状态可变性）。我们预计更高版本的 Solidity 版本将允许您的更严格的合约从此接口继承，但对于版本 0.4.24 的解决方法是，您可以在从您的合约继承之前编辑此接口以添加更严格的可变性。
- Solidity 问题 #2330：如果此规范中显示某个函数为 `external`，则如果合约使用 `public` 可见性，则该合约将是兼容的。作为版本 0.4.24 的解决方法，您可以在从您的合约继承之前编辑此接口以切换到 `public`。

_如果较新版本的 Solidity 允许在代码中表达注意事项，则可以更新此 EIP 并删除注意事项，这将等效于原始规范。_

## 理由

由于投票标准的构建旨在创建一个允许提高治理数据透明度和可访问性的系统，因此投票标准中的设计选择受到此动机的驱动。在本节中，我们将回顾一些主要的设计选择，以及做出这些选择的原因：

1. 事件日志记录：在以下情况下维护事件日志的逻辑：

   - 投票
   - 取消投票
   - 投票失败
     是为了确保在操纵选民基础的情况下，可以执行简单的链下检查以审计投票结果的完整性。

2. 没有投票结束触发器：曾考虑在投票中添加在投票完成后执行某些预先决定逻辑的函数。然而，这被认为是不必要的 - 因为这种行动可以部署在单独的合约中，该合约仅读取给定投票的结果，并且违反了模块化的精神，因为在部署投票后无法创建任何行动。此外，此类函数将无法合并投票的结果，并且肯定不适合没有结束时间的投票。

3. 允许无约束投票：与其他投票标准提案不同，投票标准不强制投票具有结束时间。这在某些情况下变得相关，在这些情况下，投票的目的是拥有一个正在进行的共识的实时注册。当您想要部署一组从投票中读取的行动合约，并且希望能够在投票达到某个阈值时执行行动合约，而不是等待投票结束时，还有一些其他用例会起作用。

4. 模块化：以太坊社区中一直有人认为不存在投票标准，因为投票合约可以是各种类型，并且具有多种形状和形式。然而，我们不同意，并论证模块化是解决方案。虽然不同的投票可能需要不同的逻辑，但它们都需要一致的终点。所有投票都需要提供结果以及人数统计，所有投票都应该具有事件日志，所有投票都应该可以使用前端工具进行检查，等等。投票标准不是说“所有投票都应该基于代币”或任何此类特定系统的声明。然而，投票标准是一个声明，即所有投票都应该具有通用的访问和修改协议 - 这将使更多的应用程序能够包含治理，而不必费心让客户开始使用命令行。

在解释了我们的理由之后，我们期待着社区的一些想法，了解如何使之更强大或更有用。

**Gas 和复杂性**（关于提案计数的枚举）

此规范考虑了包含 32 个提案样本的实现（最多达到 blockgaslimit）。如果您的应用程序能够增长并且需要超过 32 个提案，请避免在您的代码中使用 for/while 循环。这些表明您的合约可能无法扩展，并且 gas 成本会随着时间的推移而无限增长

**隐私**

个人信息：该标准不会将任何个人信息放到区块链上，因此在这方面不会损害隐私。

**社区共识**

我们在此过程中非常具有包容性，并邀请有任何问题或贡献的人参与我们的讨论。但是，此标准的编写仅用于支持本文列出的已确定的用例。
