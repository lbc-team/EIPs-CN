## 简单总结
创建一个新的交易类型，该类型执行一个或多个交易的包，同时将状态信息传递给后续交易。

## 摘要
引入一种新的交易类型，其中包括一个必须由客户端串行执行的交易列表。执行信息（例如，成功、gas_used 等）将向前传播到下一个交易。

## 动机
由于新用户需要获得足够的以太币来支付交易费用，因此让新用户加入以太坊一直非常困难。多年来，为了解决这个难题，人们投入了大量的资源。如今，解决方案是元交易。但不幸的是，这是一种脆弱的解决方案，需要从智能合约中恢复签名才能验证消息。该 EIP 旨在为中继者提供一个灵活的框架，以便他们能够以无需信任的方式一次性“赞助”多笔交易。

元交易通常使用中继合约来维护 nonce，并允许用户使用其他资产来支付 gas 费用。从历史上看，它们的设计目的是通过仅将一部分可用 gas 传递给子调用来捕获内部交易中的回滚。这使他们可以确定外部调用有足够的 gas 来完成任何所需的帐户，例如处理 gas 支付。长期以来，这种类型的子调用被认为是糟糕的做法，但在不信任子调用的情况下，这是唯一可用的解决方案。

交易包是一种替代方案，它允许将多个交易捆绑到一个包中并以原子方式执行，类似于中继合约的运作方式。交易能够将其结果传递给后续交易。这允许基于先前交易的结果进行条件工作流程。尽管上述功能已经可行，但使用交易包的工作流程更加稳健，因为它们受到未来 gas 计划变更的保护。

该 EIP 的一个重要副产品是它还有助于为单个用户捆绑交易。

## 规范
引入一个新的 [EIP-2718](./eip-2718.md) 交易类型，其中 `id = 2`。

#### 结构
```
struct TransactionPackage {
    chain_id: u256,
    children: [ChildPackage],
    nonce: u64,
    gas_price: u256,
    v: u256,
    r: u256,
    s: u256
}
```

##### 哈希
`keccak256(rlp([2, chain_id, children, nonce, gas_price, v, r, s])`

##### 签名哈希
`keccak256(rlp([2, chain_id, children, nonce, gas_price])`

##### 收据
每个 `ChildTransaction` 交易将在执行后生成一个 `ChildReceipt`。 这些收据中的每一个都将被聚合到一个 `Receipt` 中。

```
type Receipt = [ChildReceipt]
```

```
struct ChildReceipt {
    status: u256,
    cumulative_gas_used: u256,
    logs_bloom: [u8; 256],
    logs: [u8]
}
```

#### 子交易
让 `ChildPackage` 解释如下。

```
struct ChildPackage {
    type: u8,
    nonce: u64,
    transactions: [ChildTransaction],
    max_gas_price: u256,
    v: u256,
    r: u256,
    s: u256
}
```

```
struct ChildTransaction {
    flags: u8,
    to: Address,
    value: u256,
    data: [u8],
    extra: [u8],
    gas_limit: u256
}
```

##### 类型
`type` 字段用于表示 `Child` 签名者是否希望将 `max_gas_price` 和 `gas_limit` 的选择委托给 `TransactionPackage` 签名者。

| type  | signature hash  |
|---|---|
| `0x00` | `keccak256(rlp([0, nonce, transactions, max_gas_price])` |
| `0x01` | `keccak256(rlp([1, nonce, transactions_without_gas_limit])` |

### 有效性

可以按如下方式将 `TransactionPackage` 视为有效或无效。

```rust    
fn is_valid(config: &Config, state: &State, tx: TransactionPackage) bool {
    if (
        config.chain_id() != tx.chain_id ||
        tx.children.len() == 0 ||
        state.nonce(tx.from()) + 1 != tx.nonce
    ) {
        return false;
    }

    let cum_limit = tx.children.map(|x| x.gas_limit).sum();
    if state.balance(tx.from()) < cum_limit * tx.gas_price + intrinsic_gas(tx) {
        return false;
    }
    
    for child in tx.children {
        if (
            child.nonce != state.nonce(child.from()) + 1 ||
            child.value > state.balance(child.from()) ||
            child.max_gas_price < tx.gas_price
        ) {
            return false;
        }
        
        for tx in child.txs {
            if (
                tx.flags != 0 ||
                tx.extra.len() != 0 ||
                tx.gas_limit < intrinsic_gas(tx)
            ) {
                return false;
            }
        }
    }
    
    true
}
```

### 结果

后续的 `ChildTransaction` 将能够通过执行的第一帧中的 `RETURNDATACOPY (0x3E)` 接收先前 `ChildTransaction` 的结果，然后再进行任何子调用。 除了最后一个元素外，每个元素都将左侧填充 `0` 到 32 个字节。

```
struct Result {
    // Status of the previous transaction
    // 上一个交易的状态
    success: bool,
    
    // Total gas used by the previous transaction
    // 上一个交易使用的总 gas
    gas_used: u256,
    
    // Cumulative gas used by previous transactions
    // 先前交易使用的累计 gas
    cum_gas_used: u256,
    
    // The size of the return value
    // 返回值的大小
    return_size: u256,
    
    // The return value of the previous transaction
    // 上一个交易的返回值
    return_value: [u8]
}
```

### 内在成本
令交易包的内在成本定义如下：

```
fn intrinsic_gas(tx: TransactionPackage) u256 {
    let data_gas = tx.children.map(|c| c.txs.map(|t| data_cost(&c.data)).sum()).sum();
    17000 + 8000 * tx.children.len() + data_gas
}
```

### 执行
交易包应按以下方式执行：
1. 从外部签名者的余额中扣除累计成本。
2. 加载第一个子包，并执行第一个子交易。
3. 记录所有状态更改、日志、收据，并退还任何未使用的 gas。
4. 如果没有更多的子交易，请转到 `8`。
5. 计算先前执行的交易的 `Result`。
6. 准备 `Result` 以便在下一个交易的第一帧中通过返回操作码使用。
7. 执行下一个交易，然后转到 `3`。
8. 加载下一个子包，然后转到 `7`。

## 理由

### 每个 `Child` 都有自己的签名
为简单起见，作者选择要求每个子包都指定自己的签名，即使签名者与包签名者相同也是如此。 做出此选择是为了在最小化客户端更改的情况下实现最大的灵活性。 即使签名者与包签名者相同，也可以使用此交易，但代价是仅多一次签名恢复。

### `ChildPackage` 指定 `max_gas_price` 而不是 `gas_price`
允许子包指定一系列可接受的 gas 价格比静态价格更通用。 它使中继者在构建交易包方面具有更大的灵活性，并且使中继者可以尝试为交易发送者获得最佳价格。 对于固定价格，中继者可能需要用户签署多个不同的交易，并且价格各不相同。 可以通过指定最高价格并带外通信交易的紧急程度来避免这种情况（例如，中继者应立即以最高价格打包交易，而不是缓慢增加 gas 价格）。如果需要这种优化，则可以使用仅具有单个签名的未来交易类型。

### `ChildPackage` 也是类型化的
类型元素在交易类型中起着适度的作用，表示交易签名者是否希望将 gas 价格和 gas 限制的控制权委托给外部签名者。 在与受信任的中继者交互时，这是一个有用的 UX 改进，因为一旦用户决定进行交易，中继者就可以通过选择最佳 gas 价格和限制来确保将其包含在链上。

### 未使用 `flags` 和 `extra` 字段
包含这些字段是为了更好地支持将来对交易类型的更改。 这可能会与 `flags` 和 `type` 字段结合使用。 显式定义它们的一个好处是可以避免专门的 RLP 序列化，从而简化客户端和下游基础架构。 作者认为，每次交易 2 个字节的成本对于更顺畅地集成未来功能是可以接受的。

## 向后兼容性
依赖于 `ORIGIN (0x32) == CALLER (0x33) && RETURNDATASIZE (0x3D) == 0x00` 的合约现在在交易包中将始终失败，除非它们是第一个执行的交易。 目前尚不清楚是否有任何合约进行此检查。

## 安全注意事项
### 在内存池中有效管理包
引入新的交易类型带来了关于内存池的新问题。 如果以简单的方式完成，它可能会变成客户端的 DDoS 向量。 编写此 EIP 旨在尽可能减少验证的复杂性。

内存池中存在一个现有不变式，新交易希望保持该不变式，即可以在恒定时间内验证交易。 这对于打包的交易也是可能的。 RLPx 帧存在固有的 10Mb 限制，因此这将是包中可以包含的交易的上限。 另一方面，客户端也可以仅在本地配置自己的绑定（例如，包必须小于 1Mb）。 然后可以使用上述函数确定有效性。

验证包后，必须持续监控包中 nonce 是否失效。 有效实现此目的的一种潜在方法是修改内存池以对底层交易的细指针进行操作。 这将允许包提取尽可能多的“单个”交易，从而简化了监控更改的设施。 包的这些“部分”可以维护一个指向结构的指针，该结构具有指向包的所有部分的指针。 这样，只要一个部分无效，它就可以请求父级使包的所有未完成部分无效。
