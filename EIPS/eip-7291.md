## 摘要

目的绑定货币 (Purpose Bound Money, PBM) 是一种对 [ERC-1155](./eip-1155.md) 代币的封装，可用于有限的活动。本提案概述了一个智能合约接口，该接口构建于 ERC-1155 标准之上，以实现目的绑定货币 (PBM) 的概念：

- PBM 由 PBM 封装器及其封装的数字货币代币组成。数字货币代币（例如，稳定币、中央银行数字货币、代币化银行存款和类似工具）充当价值存储（缩写为“sov”）。因此，数字货币代币（也称为“sovToken”）**应该**是：
  - 良好的价值存储；
  - 合适的记账单位；以及
  - 交换媒介。
- PBM 是一种不记名工具，具有独立的编程逻辑，可以在双方之间转移，无需中介参与。它结合了以下概念：
  - 可编程支付 - 一旦满足预定义的一组条件，自动执行支付；以及
  - 可编程货币 - 将规则嵌入到交换媒介本身中，从而定义或约束其使用的可能性。
- 一旦满足条件，sovToken 就会被释放，并再次变得无界。PBM 可以被认为是一种数字现金券，因为它对付款人如何使用 PBM 施加了约束，但不对商家/兑换人施加任何约束，因为 PBM 在支付给商家/兑换人时会解包并释放底层数字货币。这类似于实物现金券：付款人只能从发行人指定的商家处购买，但接受代金券的商家可以将实物代金券与发行人兑换成法定货币。

在本 EIP 中，我们提出了一个模块化结构，包括一个与 [ERC-20](./eip-20.md) 兼容的 sovToken 作为数字货币，一个与 ERC-1155 兼容的智能合约作为 PBM 封装器，一个合规性卫士智能合约作为 PBM 封装器逻辑的组成部分，以及一个 PBM 代币管理器智能合约来管理代币注册和检索。

## 动机

目的绑定货币 (PBM) 使数字货币能够携带关于如何使用它们的条件，使其在现实场景中特别有用，例如：

- **政府代金券**（例如新加坡的 CDC 代金券），其中资金应仅可在批准的中心地带商家处兑换；
- **有条件支付**，例如 SkillsFuture 学习账户，其中资金仅在课程参与得到验证后才释放；
- **托管式支付**，例如购房者里程碑，其中支付给开发商的款项与特定建设阶段的完成相关联；

本提案旨在防止技术碎片化，从而避免缺乏互操作性。通过公开 PBM 规范，它使新的参与者能够轻松自由地访问预先存在的市场标准，从而实现跨不同平台、钱包、支付系统和渠道的互操作性。这将降低新参与者的进入成本，培养一个充满活力的支付环境，并防止围墙花园和垄断的形成，最终带来更高效、更实惠的服务和更好的用户体验。

## 规范

本文档中的关键词“必须 (MUST)”、“禁止 (MUST NOT)”、“需要 (REQUIRED)”、“应该 (SHALL)”、“不应该 (SHALL NOT)”、“应该 (SHOULD)”、“不应该 (SHOULD NOT)”、“推荐 (RECOMMENDED)”、“不推荐 (NOT RECOMMENDED)”、“可以 (MAY)”和“可选 (OPTIONAL)”应按照 RFC 2119 和 RFC 8174 中的描述进行解释。

### 定义

- **sovToken** - 一种 ERC-20 或 ERC-20 兼容的数字货币（例如 [ERC-777](./eip-777.md)、[ERC-1363](./eip-1363.md)），用作价值存储代币（即支持 PBM 代币的抵押品）。

- **PBM 封装器** - 一个符合 ERC-1155 的智能合约，它通过指定必须满足的一个或多个条件（在本提案的后续章节中称为 PBM 业务逻辑）来封装 sovToken。PBM 封装器可以设计成模块化的，包含核心、插件和钩子组件（详见 PBM 架构部分）。PBM 封装器智能合约，连同采用的钩子智能合约，在解包底层 sovToken 之前验证是否已满足条件。

- **PBM 代币** - sovToken 及其 PBM 封装器统称为 PBM 代币。PBM 代币表示为 ERC-1155 代币。

- **PBM 创建者** 定义 PBM 封装器的条件以创建 PBM 代币。

- **商家 / 兑换人** - 在本提案的上下文中，商家或兑换人被广泛定义为 PBM 代币的最终接收者或终点，这些代币本质上是定向或目的绑定的。商家/兑换人的身份将是合规性卫士执行的验证之一，合规性卫士可以作为 PBM 封装器智能合约的一部分实施，也可以作为注册为 PBM 钩子的独立合规性卫士合约实施。

### 概述

- PBM **应该** 遵守 “wrap (封装)” 或 “wrapping (封装)” 的定义，表示在其整个生命周期内按照 PBM 业务逻辑绑定代币。

- PBM **应该** 遵守 “unwrap (解包)” 或 “unwrapping (解包)” 的定义，表示在其生命周期阶段按照 PBM 业务逻辑释放代币。

- 一个有效的 PBM 代币 **必须** 由一个底层 sovToken 和一个 PBM 封装器组成。

  - sovToken 可以在创建 PBM 代币时或稍后封装。

  - sovToken 可以实现为任何广泛接受的 ERC-20 兼容代币，例如 ERC-20、ERC-777 或 ERC-1363。

- PBM 封装器 **必须** 提供一种机制，供所有交易方验证在允许 PBM 代币解包之前是否已满足所有必要的条件。有关详细说明，请参阅可审核性部分。必要的条件可以在 PBM 封装器中实施，也可以在单独的 PBM 钩子智能合约中实施。

- PBM 封装器 **必须** 确保解包的 sovToken 的目标地址位于商家/兑换人地址的白名单中，并且不在禁止地址的黑名单中，然后才能解包底层 sovToken。

- PBM 代币 **必须** 在完全解包和使用后被销毁。

- PBM 代币 **应该** 具有由 PBM 创建者决定的到期时间。

  - 对于不需要到期时间的情况，到期时间 **应该** 设置为无限大（通常表示为 uint256 的最大值或 type(uint256).max）。

- 本提案定义了 PBM 应包含内容的基本规范。对此基本规范的扩展可以作为单独的规范实施。

### PBM 架构

在本 EIP 中，我们提出了一个模块化 PBM 架构，该架构具有三个不同的组件（核心、插件和钩子）：

- **核心组件** 包含所有 PBM 都应具有的基本功能和验证检查。核心组件包括 sovToken 和包含核心逻辑的 PBM 封装器（例如，将商家/兑换人地址列入白名单的逻辑、在转移到白名单地址时解包的逻辑、铸造和销毁 PBM 的逻辑）和一个允许代币注册和检索的代币管理器。此外，PBM 封装器 **可以** 包括与插件和钩子交互的逻辑。
- **插件组件** 实现只有特定 PBM 可能需要的附加功能（例如，调用外部应用程序编程接口以验证是否满足特定 PBM 条件的逻辑、跟踪 PBM 使用模式的逻辑）。
- **钩子组件** 实现一些 PBM 可能需要的附加验证检查（例如，到期、每日消费限额、商品和服务限额等的检查）。

例如，PBM 创建者可能希望确保只有 50% 的 PBM A 系列可以在超市中使用，而 PBM B 系列在超市中使用比例没有限制。创建者可以实施一个插件智能合约来跟踪 PBM 用户在超市的消费情况，并实施一个钩子来验证分配给用户的 PBM A 系列中在超市的消费是否低于 50%。这种方法允许相同的通用 PBM 封装器和 sovToken 用于 PBM A 系列和 B 系列。此外，PBM A 系列将注册插件模块和钩子模块以进行额外的数据跟踪和验证。

### 可审计性

PBM 封装器 **应该** 提供可公开访问的机制来验证解包 PBM 的智能合约逻辑。交易方和/或列入白名单的第三方的自动验证或异步用户验证可以利用这些机制。

由于 PBM 条件的履行可能会受到审计，以确保所有交易方之间的信任，因此应记录以下证据以支持审计：

- 接口/发出的事件 **应该** 允许细粒度地重建交易历史、代币类型和代币余额
- 源代码 **应该** 在区块链浏览器上进行验证并正式发布。

### 同质化

PBM 封装器 **应该** 能够封装多种类型的兼容 sovToken（例如，同一 PBM 封装器应该能够封装 USDC 和 XSGD）。由同一 PBM 封装器封装的 sovToken 可能彼此同质化，也可能不同质化。该标准不强制规定实施必须如何执行此操作。

### PBM 代币详细信息

ERC-1155 多重代币标准使每个代币 ID 对应于唯一的、可配置的代币类型。所有促进 PBM 业务或显示逻辑的基本详细信息 **必须** 为每种代币类型定义。为此目的的强制性字段在 `struct PBMToken`（如下）中概述。未来的提案可以根据需要定义其他可选状态变量。一旦定义了代币详细信息，就 **必须** 是不可变的。

代币详细信息示例：

```solidity
pragma solidity ^0.8.0;

interface IPBMRC1_TokenManager {
    /// @notice PBM 代币必须包含强制性状态变量（名称、面值、到期时间和 uri）才能遵守此标准。
    /// @dev 表示与 PBM tokenId 对应的所有详细信息。
    struct PBMToken {
        // 代币的名称。
        string name;

        // 底层封装的 ERC20 兼容 sovToken 的值。有关 `faceValue` 的更多信息可以通过添加可选变量来指定：如下所示的 `currencySymbol` 或 `tokenSymbol`
        uint256 faceValue;

        // 代币在此时间之后将变得无用（以 Unix Epoch 时间表示）。
        uint256 expiry;

        // 用于 ERC-1155 显示的元数据 URI。
        string uri;
    }
}
```

该标准的实施者可以通过实施 `IPBMRC1_TokenManagerExt` 接口来增强其 PBM 代币的功能。此扩展提供了可选属性，可用于支持超出核心要求之外的各种用例。

```solidity
pragma solidity ^0.8.0;

interface IPBMRC1_TokenManagerExt {
    /// @notice PBM 代币可以包含的可选属性，以实现扩展功能。
    /// @dev 表示可以为 PBM tokenId 实施的其他可选字段。
    struct PBMTokenExt {
        // 指示 PBM 代币是否可以转移到非商家/兑换人钱包。
        bool isTransferable;

        // 确定 PBM 在到期时是否会在某些预定义条件下或由所有者自行决定被销毁或撤销。
        bool burnable;

        // 代币的小数位数。
        uint8 decimals;

        // 此智能合约上此 PBM 类型的创建者的地址。此字段是可选的，因为创建者默认是 msg.sender。
        address creator;

        // sovToken 的智能合约地址。
        address tokenAddress;

        // 已铸造的 PBM 代币类型的运行余额。
        uint256 totalSupply;

        // 在多货币 PBM 用例中，可能需要 ISO4217 三字符字母代码来表示面值。
        string currencySymbol;

        // 可以分配 PBM 代币名称的缩写。
        string tokenSymbol;

        // 在下面添加其他可选状态变量...
    }
}
```

实施者可以选择在 PBM 合约部署时定义所有代币类型。如果需要，他们还可以公开一个外部函数以在稍后创建新的 PBM 代币。
所有创建的代币类型 **应该** 发出 `NewPBMTypeCreated` 事件。

```solidity
    /// @notice 使用提供的数据创建新的 PBM 代币类型。
    /// @dev createPBMTokenType 的调用者应负责设置创建者地址。
    /// [`sample-uri`](../assets/eip-7291/sample-uri/stx-10-static) 中可以找到 uri 的示例
    /// 必须发出 {NewPBMTypeCreated} 事件
    /// @param _name 代币的名称。
    /// @param _faceValue 底层封装的 ERC20 兼容 sovToken 的值。
    /// @param _tokenExpiry 代币在此时间之后将变得无用（以 Unix Epoch 时间表示）。
    /// @param _tokenURI 用于 ERC-1155 显示的元数据 URI
    function createPBMTokenType(
        string memory _name,
        uint256 _faceValue,
        uint256 _tokenExpiry,
        string memory _tokenURI
    ) external returns (uint256 tokenId_);

    /// @notice 当在合约中创建新的目的绑定代币 (PBM) 类型时发出。
    /// @param tokenId 新创建的 PBM 代币类型的唯一标识符。
    /// @param tokenName 一个人类可读的字符串，表示新创建的 PBM 代币类型的名称。
    /// @param amount 新创建的 PBM 代币类型的初始供应量。
    /// @param expiry 新创建的 PBM 代币类型到期的时间戳。
    /// @param creator 创建新 PBM 代币类型的帐户地址。
    event NewPBMTypeCreated(uint256 tokenId, string tokenName, uint256 amount, uint256 expiry, address creator);

```

该标准的实施者 **必须** 定义一种检索 PBM 代币详细信息的方法

```solidity
    /// @notice 检索给定 tokenId 的 PBM 代币类型的详细信息。
    /// @dev 此函数获取与 tokenId 关联的 PBMToken 结构并返回它。
    /// @param tokenId PBM 代币类型的标识符。
    /// @return pbmToken_ 一个包含指定 PBM 代币类型的所有详细信息的 PBMToken 结构。
    function getTokenDetails(uint256 tokenId) external view returns(PBMToken memory pbmToken_);
```

### Compliance Guard (合规性卫士)

合规性卫士应该具有存储和检索白名单商家/兑换人和黑名单地址的逻辑，以实现 PBM 的基本前提。可以添加其他逻辑来实现其他合规性目标。

```solidity
pragma solidity ^0.8.0;

/// @title Compliance Guard Interface (合规性卫士接口)。
/// @notice 合规性卫士存储和管理 PBM 的白名单商家/兑换人和黑名单地址
interface IComplianceGuard {
    /// @notice 检查地址是否为黑名单地址之一
    /// @param _address 要查询的地址
    /// @return bool_ 如果地址在黑名单中，则为 True，否则为 false
    function isBlacklisted(address _address) external returns (bool bool_) ;

    /// @notice 检查地址是否为白名单商家/兑换人地址之一
    /// @param _address 要查询的地址
    /// @return bool_ 如果地址在商家/兑换人白名单中并且不是黑名单地址，则为 True，否则为 false。
    function isMerchant(address _address) external returns (bool bool_) ;

    /// @notice 当编辑商家/兑换人列表时发出事件
    /// @param action 动作类型的标签 “add (添加)” 或 “remove (删除)”
    /// @param addresses 刚刚添加到商家/兑换人白名单或从商家/兑换人白名单中删除的商家钱包地址数组
    /// @param metadata 关于添加或删除的地址的可选评论或注释。
    event MerchantList(string action, address[] addresses, string metadata);

    /// @notice 当编辑黑名单时发出事件
    /// @param action 动作类型的标签 “add (添加)” 或 “remove (删除)”
    /// @param addresses 刚刚添加到地址黑名单或从地址黑名单中删除的钱包地址数组
    /// @param metadata 关于添加或删除的地址的可选评论或注释。
    event Blacklist(string action, address[] addresses, string metadata);
}

```

### PBMRC1 - 基础接口

此接口包含实现预加载 PBM 所需的基本功能。

```solidity
pragma solidity ^0.8.0;

/// 要发出的事件列表
/// 数据库或浏览器可以监听事件，并能够提供索引和分类搜索
/// @title PBM Specification interface (PBM 规范接口)
/// @notice PBM（目的绑定货币）允许我们对 sovToken 的使用添加逻辑要求。
/// PBM 充当 sovToken 的封装器并实施必要的业务逻辑。
/// @dev PBM 部署者必须为智能合约分配一个总所有者。如果需要细粒度的访问控制，则可以在 ERC173 之上使用 EIP-5982
interface IPBMRC1 is IERC173, IERC5679Ext1155 {

    /// @notice 通过指定底层 ERC20 兼容代币地址、合约到期时间和 PBM Wrapper Logic 智能合约的地址来初始化合约。
    /// @param _sovToken 底层 sovToken 的地址。
    /// @param _expiry 合约范围的到期时间戳（以 Unix epoch 时间表示）。
    /// @param _pbmWrapperLogic 此地址应指向包含管辖 PBM 的条件的智能合约；
    /// 例如，目的绑定条件（例如，确定是否允许转移或解包 PBM 的合规性卫士）
    /// 和其他相关的业务逻辑，有效地实现了控制反转。
    function initialise(address _sovToken, uint256 _expiry, address _pbmWrapperLogic) external;

    /// @notice 返回具有相应 tokenId 的 PBM 的统一资源标识符 (URI) 元数据信息。
    /// @dev URI 在 RFC 3986 中定义。
    /// URI 必须指向符合 “ERC-1155 元数据 URI JSON 模式” 的 JSON 文件。
    /// 如果需要，开发人员可以选择遵守 ERC1155Metadata_URI 扩展接口。
    /// URI 不应是不可变的。
    /// @param tokenId 查询中 PBM 的 id
    /// @return 返回 PBM 的元数据 URI 字符串
    function uri(uint256 tokenId) external  view returns (string memory);

    /**
        @notice 创建现有 PBM 代币类型的 PBM 副本（ERC1155 NFT）。
        @dev 有关更多实施说明，请参阅 {IERC5679Ext1155}
        @param receiver 需要将创建的 PBM 转移到的钱包地址
        @param tokenId 要复制的 PBM 代币类型的标识符。
        @param amount 要创建的 PBM 的数量
        @param data 没有指定格式的其他数据，基于 EIP-5750

        此函数将底层代币从调用者转移到 PBM 智能合约。
        IMPT：在铸造之前，调用者应批准合约地址代表调用者使用 sovToken。
            这可以通过调用 ERC-20 合约的 `approve` 或 `increaseMinterAllowance` 函数并将 `_spender` 指定为 PBM 合约地址来完成。
            参考：https://eips.ethereum.org/EIPS/eip-20

        警告：任何外部调用这些 safeMint() 和 safeMintBatch() 函数的合约都应实施某种重入保护程序
        （例如 OpenZeppelin 的 ReentrancyGuard）或检查效果交互模式。

        根据 ERC-5679 标准：当代币被铸造时，转移事件必须像 EIP-1155 的 `amount` 中的代币一样发出
        并且 EIP-1155 的 `tokenId` 是 _id，从地址 0x0 转移到接收者地址（由接收者标识）。
        总供应量必须相应增加。

        必须在铸造期间发出 {TokenWrap} 事件，因为底层 sovToken 由 PBM 封装器智能合约封装。

        要求：
        - 合约不得暂停
        - 代币不得过期
        - `tokenId` 应是已创建的有效 id
        - 调用者应具有铸造所需的必要数量的 sovToken
        - 调用者应已批准 PBM 合约使用 sovToken
        - 接收者不应被列入黑名单
     */
    function safeMint(address receiver, uint256 tokenId, uint256 amount, bytes calldata data) external;

    /**
```

## 理论基础

### 为什么 sovToken **必须**与 ERC-20 兼容？

由于 PBM 被设想为具有货币的功能，因此它必须是一种具有稳定价值的可替代代币。目前，市场上主要的稳定币主要基于 ERC-20 接口。ERC-20 或 ERC-20 兼容代币是现有钱包、DeFi 应用程序最广泛支持的，也被 [ERC-4337](./eip-4337.md) 等协议设计使用，更重要的是，它们是可替代代币的事实标准。

关于 [ERC-721](./eip-721.md) 和 ERC-1155 兼容代币：

- ERC-721 不适用，因为它是一种非同质化代币的标准，不能履行货币的功能。
- 虽然 ERC-1155 代币可以用于同质化代币，但我们决定不包括它，因为市场上缺乏 ERC-1155 稳定币。要求 PBM 接口同时支持 ERC-20 兼容和 ERC-1155 兼容的 sovToken 会使 PBM 接口复杂化，而不会增加太多实际效用。此外，基本 ERC-1155 不支持小数，但这不是一个阻碍，因为可以有变通方法。但是，如果未来稳定币市场发生变化，可以考虑进行修订。

### 为什么 PBM 包装器 **必须**与 ERC-1155 兼容？

本文档扩展了 ERC-1155 标准，以便现有钱包提供商可以轻松采用。目前，大多数钱包提供商都能够支持和显示 ERC-20、ERC-1155 和 ERC-721 标准。不扩展这些标准的实现将要求钱包提供商构建自定义用户界面和接口逻辑，从而增加实现成本并延长上市时间。

我们提案的核心目标是标准化 PBM 的实现。因此，我们调查了现有的接口标准，并决定基于 ERC-1155 标准构建 PBM 代币，原因如下：

- ERC-1155 允许单个合约支持多个代币。这对于 PBM 用例非常有用，因为单个合约可以支持发行具有不同面额、到期日、业务逻辑的代币。
- ERC-1155 还具有批量转账支持，这是 ERC-20 中没有的，当必须将代币空投给大量接收者时，这可以节省 Gas 费用。
- ERC-1155 能够支持半同质化代币，这对于 PBM 用例非常有用，因为 PBM 可以在到期后转换为收藏品。
- ERC-1155 允许在钱包发行商的 UI 上可视化 PBM 代币。

### 为什么 PBM **必须**确保解包 sovToken 的目标地址位于商家/赎回者地址的白名单中，并且不在禁止地址的黑名单中，然后才能解包底层 sovToken？

为什么我们需要白名单？

- 白名单是一项强制性要求，因为 PBM 是有目的约束的，即只有在满足所有条件且转移给预定义白名单中的某人时才应解包。
- 在某些实现中，开发人员可以在运行时动态定义列入白名单的地址，例如要求钱包地址中存在 NFT 或依赖预言机等。

为什么我们需要黑名单？

- 黑名单是一项强制性要求，以确保因各种原因被禁止的帐户（例如，地址所有者已重新注册新帐户，地址所有者因投诉或执法原因而被暂停、撤回或驱逐等）被排除在外。

为什么我们不能只有白名单或黑名单？

- 虽然可以通过仅拥有白名单来实现相同的效果，但为了禁止一个人而反复将白名单重新部署到区块链并非 Gas 有效。
- 仅使用黑名单来实现有目的约束的货币是不切实际的，因为它需要维护所有要排除的地址的列表，并在每次创建新帐户时更新它。

为什么需要目的地？

- 这构成了我们提案的核心：只有当 PBM 被转移到预先批准的目的地时，才能解包。
- PBM 可以自由转移，但只允许目标解包 PBM 并交付底层 sovToken 必须受到限制，以区别于智能合约包装的普通香草稳定币。

### 业务逻辑包含什么？

- 一般来说，业务逻辑可以分为核心逻辑、插件逻辑和钩子逻辑：
  - 核心逻辑包含基本功能和验证检查，应包含在 PBM 包装器合约中。
  - 插件和钩子逻辑可以作为独立的智能合约模块实现，并由 PBM 包装器合约注册。插件逻辑通过添加功能来扩展核心逻辑，例如自定义数据收集、其他管理功能等。
  - 钩子逻辑实现额外的验证检查，这些检查仅适用于 PBM 的子集。
- “PBM 业务逻辑”可以包含访问控制逻辑、PBM 解包逻辑、与非区块链 IT 系统集成的 API 逻辑。
- 由于 PBM 可以用于各种各样的用例，从政府支付代币、购物优惠券、预付代币、奖励积分代币、有目的约束的捐赠代币、学校津贴代币等，每个用例都有单独的业务逻辑，因此有意未定义，以便实现作者可以拥有最大的灵活性。

### 为什么选择推送交易模型？

- 此标准坚持推送交易模型，其中 PBM 的转移是在发件人端发起的。现代钱包可以通过将解包逻辑嵌入到 ERC-1155 `safeTransfer` 函数中来支持所需的 PBM 逻辑。

### 可定制性

每个 ERC-1155 PBM 代币都将映射到底层 `PBMToken` 数据结构，实现者可以自由地根据业务逻辑进行自定义。

通过将底层 ERC-1155 代币模型与附加的数据结构映射，实现者可以灵活地在同一智能合约中管理多个代币类型，并将多个有条件解包逻辑附加到每个代币类型，从而降低 Gas 成本，因为无需为每种代币类型部署多个智能合约。

1. 为了简单起见，此标准_有意_省略了未添加到 PBM 的定义和概念的函数或事件。

2. 此 EIP 不对访问控制或可以执行函数的条件做任何假设。PBM 创建者有责任确定每个特定 PBM 业务流程中涉及的各种角色。

3. 提议的 PBM 架构_有意_采用模块化设计，以实现更大的可定制性和智能合约的重用性。

4. 与 PBM 标准关联的元数据不包含在该标准中。如有必要，可以使用单独的元数据扩展接口创建相关的元数据，例如来自 ERC-721 的 `ERC721Metadata`。有关实现示例，请参阅 Opensea 的 metadata-standards。

5. 为了允许未来的可扩展性，**建议**开发人员阅读并采用用于构建方法行为的通用可扩展性的规范 ([ERC-5750](./eip-5750.md))。

## 安全考虑

- 恶意用户可能会尝试：

  - 通过重入进行双重支付。
  - 克隆现有的 PBM 代币以执行双重支付；
  - 创建没有底层 sovToken 的无效 PBM 代币；或者
  - 通过包装欺诈/无效/毫无价值的 sovToken 来伪造 PBM 代币的面值。

- 为了保持一致性，当合约被暂停或用户的代币转移因涉嫌欺诈活动或错误转移而受到限制时，**必须**对用户的 PBM 代币解包请求施加相应的限制。

- 应执行安全审计和测试，以验证解包逻辑是否按预期运行，或者是否正在实施涉及调用外部智能合约的任何复杂业务逻辑，以防止重入攻击和其他形式的调用链攻击。

- 此 EIP 依赖于代币实现的安全和准确的簿记行为。

  - 遵守此标准的合约应密切监控每个用户在代币消费或铸造期间的余额变化。

  - PBM 包装器必须经过精心设计，以确保有效控制铸造新代币的权限。未能保护铸造权限可能会导致欺诈发行和未经授权的代币总供应量膨胀。

  - 将每个 PBM 代币映射到智能合约持有的相应数量的底层 sovToken 需要仔细的核算和审计。

  - 应仔细设计对销毁代币权限的访问控制。通常，只有以下两个角色有权销毁代币：

    - 角色 1. 在 PBM 到期之前，只有具有非黑名单钱包地址的白名单商家/赎回者才允许解包和销毁他们持有的代币。
    - 角色 2. 在 PBM 到期后：
      - 具有非黑名单钱包地址的白名单商家/赎回者被允许解包和销毁他们持有的代币；并且
      - PBM 所有者被允许销毁非白名单商家/赎回者手中剩余的未使用的 PBM 代币，以检索底层 sovToken。

  - 然而，我们确实认识到可能存在其他用例，其中第三种类型的角色可能有权进行销毁。在设计对销毁 PBM 代币的访问控制时，实施者应谨慎。

- 建议采用与 ERC-20 兼容的 sovToken 标准。此类兼容代币的示例包括实现 ERC-777 或 ERC-1363 的代币。但是，由于其简单性，ERC-20 仍然是最广泛接受的，并且对其安全性具有很高的信心。
