## 摘要
本提案为描述类以太坊链的远程过程调用（RPC）提供者列表指定了一个 JSON 模式，包括它们支持的 [EIP-155](./eip-155.md) `CHAIN_ID`。

## 动机
最近涌现出大量的替代链、扩展解决方案和其他主要与以太坊兼容的账本，给用户带来了许多风险。盲目地使用 [EIP-3085](./eip-3085.md) 添加新的 RPC 提供者而不评估他们的可信度已经变得司空见惯。在最好的情况下，这些 RPC 提供者可能是准确的，但会跟踪请求；在最坏的情况下，他们可能会提供误导性信息并抢先交易。

如果用户获得由他们的钱包直接构建的综合提供者列表，并可以选择切换到他们选择的任何列表，那么这些恶意提供者的风险将大大降低，而不会牺牲高级用户的功能。

## 规范

本文档中的关键词“必须（MUST）”，“禁止（MUST NOT）”，“必需（REQUIRED）”，“应当（SHALL）”，“不应当（SHALL NOT）”，“应该（SHOULD）”，“不应该（SHOULD NOT）”，“推荐（RECOMMENDED）”，“可以（MAY）”和“可选（OPTIONAL）”应按照 RFC 2119 中描述的进行解释。

### 列表验证 & 模式

列表消费者（如钱包）必须根据提供的模式验证列表。列表消费者不得连接到仅在无效列表中存在的 RPC 提供者。

### 版本控制

列表版本控制必须遵循 [语义化版本控制 2.0.0](../assets/eip-5139/semver.md) (SemVer) 规范。

对于以下修改，必须增加主版本号：

 - 删除一个提供者。
 - 更改 `providers` 对象中提供者的键。
 - 删除链 ID 的最后一个 `ProviderChain`。

对于 SemVer 允许的其他修改，可以增加主版本号。

如果未增加主版本号，则如果进行以下任何修改，则必须增加次版本号：

 - 添加一个提供者。
 -添加链 ID 的第一个 `ProviderChain`。

对于 SemVer 允许的其他修改，可以增加次版本号。

如果主版本号和次版本号未更改，则对于任何更改都必须增加补丁版本号。

### 发布

提供者列表应该使用 [EIP-1577](./eip-1577.md) 的 `contenthash` 机制在主网上发布到以太坊名称服务（ENS）名称。

提供者列表也可以使用 HTTPS 发布。以这种方式发布的提供者列表必须允许来自其他来源的合理访问（通常通过设置标头 `Access-Control-Allow-Origin: *`。）

### 优先级

提供者条目可以包含 `priority` 字段。值为零的 `priority` 应指示最高优先级，增加的 `priority` 值指示优先级降低。可以为多个提供者分配相同的优先级。所有没有 `priority` 字段的提供者应具有相同的优先级。没有 `priority` 字段的提供者应始终比具有 `priority` 字段的任何提供者具有更低的优先级。

列表使用者可以使用 `priority` 字段来选择何时连接到提供者，但可以完全忽略它。列表使用者应该向用户解释他们的实现如何解释 `priority`。

### 列表子类型

提供者列表分为两个类别：根列表和扩展列表。根列表包含提供者列表，而扩展列表包含要应用于另一个列表的一组修改。

#### 根列表

根列表具有顶级 `providers` 键。

#### 扩展列表

扩展列表具有顶级 `extends` 和 `changes` 键。

##### 指定父列表 (`extends`)

`uri` 和 `ens` 字段应指向父列表的来源。

如果存在，`uri` 字段必须使用 [发布](#publishing) 中指定的方案。

如果存在，`ens` 字段必须指定一个使用 EIP-1577 解析的 ENS 名称。

`version` 字段应指定兼容版本的范围。列表消费者必须拒绝指定不兼容的父版本的扩展列表。

如果版本不兼容，列表消费者可以继续使用先前保存的父列表，但选择这样做的列表消费者必须显示一个显眼的警告，提示提供者列表已过期。

###### 默认模式

如果省略 `mode` 字段，则当且仅当父版本号与主版本号、次版本号、补丁版本号分组中最左边的非零部分匹配时，父版本才是兼容的。

例如：

```javascript
{
  "major": "1",
  "minor": "2",
  "patch": "3"
}
```

相当于：

```
>=1.2.3, <2.0.0
```

并且：

```javascript
{
  "major": "0",
  "minor": "2",
  "patch": "3"
}
```

相当于：

```
>=0.2.3, <0.3.0
```

###### Caret 模式 (`^`)

`^` 模式的行为应与上面的默认模式完全相同。

###### 精确模式 (`=`)

在 `=` 模式下，当且仅当父版本号与指定的版本完全匹配时，父版本才是兼容的。

`changes` 字段应为 RFC 6902 中指定的 JavaScript 对象表示法（JSON）补丁文档。

##### 应用扩展列表

列表使用者必须遵循此算法来应用扩展列表：

 1. 当前列表是扩展列表吗？
    * 是：
       1. 确保之前没有见过此 `from`。
       1. 检索父列表。
       1. 验证父列表是否根据 JSON 模式有效。
       1. 确保父列表的版本兼容。
       1. 将当前列表设置为父列表，然后转到步骤 1。
    * 否：
       1. 转到步骤 2。
 2. 将当前列表复制到一个变量 `$output` 中。
 3. 当前列表是否有子列表：
    * 是：
       1. 将子列表的 `changes` 应用于 `$output` 中的 `providers`。
       1. 验证 `$output` 是否根据 JSON 模式有效。
       1. 将当前列表设置为子列表。
       1. 转到步骤 3。
    * 否：
       1. 将当前列表的 `providers` 替换为 `$output` 中的 `providers`。
       1. 当前列表现在是已解析的列表；返回它。


列表消费者应该将扩展列表的数量限制为合理的数量。

## 理由

此规范具有两个层（提供者，然后是链 ID），而不是更扁平的结构，以便钱包可以选择为同一查询查询多个独立的提供者并比较结果。

每个提供者可以指定多个端点来实现负载平衡或冗余。

列表版本标识符符合 SemVer，以大致传达每个新版本带来的更改类型。如果新版本添加了功能（例如，新的链 ID），则用户可以期望增加次版本号。同样，如果未增加主版本号，则列表订阅者可以假定在当前版本中工作的 DApp 将继续在下一个版本中工作。

## 安全注意事项

最终，由最终用户决定订阅哪个列表。大多数用户不会更改钱包维护的默认列表。由于钱包已经可以访问私钥，因此赋予它们对 RPC 提供者的额外控制似乎只会略微增加风险。

虽然列表维护者可能会受到激励（可能是在经济上）以包含或排除特定的提供者，但实际上这样做可能会损害其列表的合法性。此标准有助于交换列表，因此，如果揭示了此类操纵，则用户可以自由地切换到新的列表，而无需付出任何努力。

如果用户选择的列表是使用 EIP-1577 发布的，则列表使用者必须以某种方式访问 ENS。这会产生一个悖论：如何在没有 RPC 提供者的情况下查询以太坊？此悖论创建了一个攻击向量：列表使用者用于获取列表的任何方法都可以跟踪用户，甚至更严重的是，**可以谎报列表的内容**。
