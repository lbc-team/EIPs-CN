## 简单总结
代理合约正越来越多地被用作升级机制，以及在部署特定合约的多个实例时节省 gas 的一种方式。本标准提出了一组代理的接口，用于表明它们如何工作以及它们的主要实现是什么。

## 摘要
使用将其自身的逻辑委托给另一个合约的代理正成为智能合约升级和创建廉价克隆合约的一种越来越流行的技术。

我们不认为标准化 DelegateProxy 的任何特定实现有任何价值，因为它的简单性，但我们认为在就所有代理使用的接口达成一致方面有很多价值，该接口允许以标准方式与代理进行操作。

## 标准化接口

```solidity
interface ERCProxy {
  function proxyType() public pure returns (uint256 proxyTypeId);
  function implementation() public view returns (address codeAddr);
}
```

### 代码地址 (`implementation()`)
返回的代码地址是代理在那个时间点，对于该消息，会将调用委托到的地址。

### 代理类型 (`proxyType()`)

检查代理类型是检查合约是否为代理的方式。当合约未能返回到此方法或返回 0 时，可以假定该合约不是代理。

它还允许传达更多关于代理如何运作的信息。它是一个纯函数，因此使其有效地保持不变，因为它不能根据状态变化返回不同的值。

- **转发代理** (`id = 1`): 代理将始终转发到相同的代码地址。以下不变式应始终为真：一旦代理返回一个非零代码地址，该代码地址永远不应改变。

- **可升级代理** (`id = 2`): 代理代码地址可以根据在代理级别或其转发逻辑中实现的任意逻辑进行更改。

## 益处

- **源代码验证**: 现在，当在像 Etherscan 这样的浏览器中检查代理的代码时，它只显示代理本身的代码，而不显示合约的实际代码。通过标准化这个构造，它们将能够显示合约的实际 ABI 和代码。
