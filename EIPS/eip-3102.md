## 简述

将存储结构从十六进制改为二进制，合并账户和存储 Trie，并使用 blake2b。

## 摘要

本提案提出了一种用于账户和存储 Trie 的二进制结构和 Merkelization 规则，它们被合并成一个单一的“状态” Trie。为了简化设计，RLP 以及 MPT 的大多数优化都被放弃。Keccak256 被 blake2b 替换。

## 动机

当前 Merkle Patricia Trie (MPT) 的设计使用了一个十六进制 Trie。十六进制 Merkle 树比其二进制对应物更浅，这意味着更少的哈希运算。
在以太坊存在的 5 年时间里，磁盘访问显然比哈希运算更是一个瓶颈。因此，客户端正在放弃一种存储所有内部节点的存储模型，转而采用由 turbo-geth 首次使用的扁平 (key, value) 存储模型，在这种模型中，中间节点仅在需要时才重新计算。

人们正在推动使以太坊更容易以无状态方式使用。二进制 Trie 比十六进制 Trie 提供更小 (~4x) 的证明，使其成为无状态友好的以太坊的首选设计。

出于同样的原因，账户和存储 Trie 被合并，以便对所有更改进行单一证明。

MPT 的设计也充满了对大小的奇怪优化，这些优化效果有限 - 但却以令人望而却步的复杂性为代价。例如，对于 RLP 小于 32 字节的子节点进行嵌套，估计可以节省 1MB 的磁盘空间。与撰写本文时快速同步所需的 300GB 相比，这简直是微不足道。这些优化是错误的重要来源，因此存在共识破坏的风险。
对 RLP 的依赖也因其复杂性而受到批评，而通用编码方案的开销对于 Merkle Trie 的刚性结构而言是不必要的。

将存储模型从十六进制 Trie 切换到二进制 Trie 的愿望提供了一个采用更简单的 Trie 架构的机会，该架构将优化从协议层面下推到客户端实现者的层面。

## 规范

### 约定

| 代码      | 描述                                                                                                |
| :-:       | -                                                                                                  |
| `u256(x)` | 数字 _x_ 的大端，32 字节表示                                                                                       |
|`||`          | 字节级连接运算符                                                                                                    |
| `++`         | 位级连接运算符                                                                                                        |
| `0b0101`     | 二进制字符串 `0101`                                                                                                   |
| `hash()`     | 常规哈希函数                                                                                                        |
| `empty_hash` | 空哈希：`hash("")`                                                                                                 |
| `length(x)`  | 对象 `x` 的字节长度                                                                                                    |
| `d[a..b]`    | 从字节序列 `d` 中获取的大端位序列，从位索引 `a` 开始，到包括索引 `b` 的位。                                                           |

### 与十六进制结构相比的显著变化

 * 账户和存储 Trie 被合并，密钥长度在 32 到 64 字节之间；
 * 不再使用 RLP；
 * 在十六进制前缀中使用的“叶子标记”位也被删除。叶子被识别为没有子节点的节点；
 * 序列化节点被哈希，无论序列化节点的字节长度有多小。

### Trie

#### 结构

Trie 结构由 _nodes_ 组成。一个节点 `N ≡ (N_l,N_r,N_p,N_v)` 具有以下 4 个组成部分：

 * `N_l` 是指向节点 _左子节点_ 的哈希。如果该节点没有左子节点，则 `N_l` 是空哈希 `empty_hash`；
 * `N_r` 是指向节点 _右子节点_ 的哈希。如果该节点没有右子节点，则 `N_r` 是空哈希 `empty_hash`；
 * 可选的 `N_p` 是节点的 _前缀_：以 `N` 为根的子 Trie 中的每个密钥都以此位字符串为前缀；
 * `N_v` 是存储在此节点上的 _值_。该值**仅存在于叶子节点中**。

以 `empty_hash` 作为两个子节点的节点称为 _叶子节点_，其余节点称为 _内部节点_。

#### 访问账户的余额、nonce、代码、存储根和存储槽

假设地址为 `A_a` 的账户 `A ≡ (A_b, A_n, A_c, A_s)`，则可以在以下地址找到以下元素：

 * 账户余额 `A_b` 可以在密钥 `hash(A_a)[0..253] ++ 0b00` 处找到，类型为 `uint256`；
 * 账户 nonce `A_n` 可以在密钥 `hash(A_a)[0..253] ++ 0b01` 处找到，类型为 `uint64`；
 * 代码 `A_c` 是一个任意长度的字节序列，可以在密钥 `hash(A_a)[0..253] ++ 0b10` 处找到；
 * 存储 Trie 的根 `A_s` 可以在密钥 `hash(A_a)[0..253] ++ 0b11` 处找到
     * 存储槽号 `k` 可以在密钥 `hash(A_a)[0..253] ++ 0b11 ++ hash(k)` 处找到。

在 [EIP-2926](./eip-2926.md) 推出后，`A_c` 将代表代码 Merkelization 树的根。访问代码块号 `c` 的密钥是 `hash(A_a)[0..253] ++ 0b10 ++ u256(c)`。

在不太可能的未来情况下，如果需要在帐户级别向 Trie 添加额外项目，则可以为将来使用保留第三位。

### 节点 Merkelization 规则

没有前缀的叶子和节点根据以下规则进行哈希：

```
internal_hash = hash(left_child_hash || right_child_hash)
leaf_hash = hash(hash(key) || hash(leaf_value))
```

如果存在前缀，则从根到前缀节点的路径长度与无前缀规则的输出进一步连接，并再次哈希：

```
internal_hash_with_prefix = hash(u256(path_length_u256 - 1) || internal_hash)
leaf_hash_with_prefix = hash(u256(path_length_u256 - 1) || leaf_hash)
```

## 基本原理

### blake2b

BLAKE2 提供了更好的性能，这对于弥补与节点数量增加约 4 倍相关的性能损失至关重要。

BLAKE3 提供更好的性能。在撰写本文档时，没有正式的 golang 版本发布。这存在安全风险，因此考虑使用 BLAKE2。

### 合并帐户和存储 Trie

客户端的趋势是将密钥和值存储在“扁平”数据库中。任何存储槽的密钥都以其所属帐户的地址密钥作为前缀，这有助于将帐户的所有数据分组到磁盘上，并简化了见证结构。

### 前缀和扩展节点

已经提出了一个替代方案，该方案提供了最佳的见证。权衡是必须删除扩展节点。

```
node_hash = hash(left_child_hash || right_child_hash)
leaf_hash = hash(0 || leaf_value)
```

删除扩展节点会导致 40 倍更高的哈希成本（对于只有 1k 个叶子的 Trie，约为 25 毫秒），因此它们被保留了下来。

可以在[这里](https://notes.ethereum.org/m5VMkX8FRvi0Q_OOR7TF4A)找到保持扩展节点用于见证而不是 Merkelization 规则的尝试。

摆脱像 RLP、十六进制前缀和子节点嵌套这样的复杂方法已经在提供很大的简化。

### 2x32 字节输入

已经要求将每个节点哈希计算保持为一个函数，该函数将两个 256 位整数作为输入并输出一个 256 位整数。预计此属性与电路结构配合良好，因此有望极大地帮助未来的零知识应用程序。

### 二进制 Trie

选择二进制 Trie 主要是因为它们减少了见证大小。一般来说，在具有 `N` 个元素的树中，每个元素有 `k` 个子节点，分支的平均长度大约是 `32 * (k-1) * log(N) / log(k)` 加上几个百分比的开销。32 是哈希的长度；`k-1` 指的是这样一个事实，即 Merkle 证明需要提供每个级别的所有 `k-1` 个姊妹节点，并且 `log(N) / log(k)` 是树中级别数的近似值（例如，一个树，其中每个节点有 5 个子节点，总共有 625 个节点，深度为 4，因为 `625 = 5**4`，所以 `log(625) / log(5) = 4`）。

对于任何 `N`，表达式在 `k = 2` 时最小化。这是一个假设 `N = 2**24` 的不同 `k` 值的分支长度表：

| `k`（每个节点的子节点数） | 分支长度（块） | 分支长度（字节） |
| - | - | - |
| 2 | 1 * 24 = 24 | 768 |
| 4 | 3 * 12 = 36 | 1152 |
| 8 | 7 * 8 = 56 | 1792 |
| 16 | 15 * 6 = 90 | 2880 |

由于不均匀的分布和开销，实际分支长度将略大于此值，但 `k=2` 是迄今为止最佳的模式仍然存在。

以太坊树最初是十六进制的，因为这将减少数据库读取的次数（例如，在上面的示例中为 6，而不是 24）。现在人们了解到这种推理是有缺陷的，因为节点仍然可以“假装”二进制树是数据库层上的十六进制（甚至 256 进制）树（例如，参见 https://ethresear.ch/t/optimizing-sparse-merkle-trees/3751），从而获得两全其美的效果，即从哈希结构的角度来看，树的证明大小较低，并且同时在数据库中具有更高效的表示。

此外，预计二进制树将在 Eth2 中广泛使用，因此该路径提高了向前兼容性并降低了协议的长期总复杂度。

### 路径长度而不是位前缀

为了消除与字节操作相关的复杂性，仅使用扩展的位长度来 Merkelize 具有前缀的节点。

存储从根节点到节点的路径长度，而不是从父节点到节点的路径长度，这具有一个优点，即在删除叶子时不需要哈希兄弟节点。

![Sibling deletion diagram](../assets/eip-3102/sibling.svg)

_左边是一个带有前缀长度的 Trie，右边是一个带有完整路径长度的 Trie。每个都有值 `10000100` 和 `10000000`。在删除 `10000100` 之后，必须在左侧树中更新兄弟节点，而在右侧树中则不必这样做。_

### 值哈希

除了代码之外，Trie 中的所有值都小于 32 字节。EIP-2926 引入了代码块，其中 `CHUNK_SIZE = 32 bytes`。因此可以保存叶子值的哈希。但是，EIP 的作者正在考虑将来增加 `CHUNK_SIZE`，这使得 `hash(value)` 成为面向未来的选择。

## 向后兼容性

需要进行硬分叉，以便块具有使用不同结构的 Trie 根。
